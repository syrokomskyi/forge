# Publishing @warpgogol/forge

## How it works

1. The source lives in the [warpgogol/werkstatt](https://github.com/syrokomskyi/werkstatt) monorepo under `packages/forge/`.
2. [`@warpgogol/repo-extract`](https://github.com/syrokomskyi/repo-extract) extracts the package into the standalone [syrokomskyi/forge](https://github.com/syrokomskyi/forge) repository, flattening to repo root and stripping workspace dependencies.
3. The generated GitHub Actions CI workflow (`.github/workflows/ci.yml`) runs on every push to `main`: lint → typecheck → build → test → `npm publish --provenance --access public`.
4. The `NPM_TOKEN` secret must be set in the [repository settings](https://github.com/syrokomskyi/forge/settings/secrets/actions).

## Triggering a new release

From the werkstatt monorepo root (operator acts, RFC-1499):

```sh
werkstatt run flow.cut --lines forge          # writes the version, lands the release, tags forge@X.Y.Z
werkstatt run flow.digest                   # review the outbound digest
werkstatt run flow.push --digest <digestId> # the only outbound step
```

`flow.cut` + `flow.push` (RFC-1490/1491/1499) is the **only** supported export path — the retired `scripts/publish-forge.mjs`/`bump-forge.mjs` were removed by the fixed-branch switch-over. The pipeline:

1. `flow.cut --lines forge` bumps `packages/forge/package.json` + `forge.yaml` `syncedVersion` via verified JSON-equal replacements (FLOW-CUT-11), lands `chore(release): forge@X.Y.Z` into `develop` under the integration lock + gate, fast-forwards `main`, and writes the `forge/release-tag@1` annotated tag. A `major` level requires `ALLOW_MAJOR_BUMP=1` (FLOW-CUT-05). Reruns resume from the tip's `chore(release):` subject — no version is ever skipped.
2. `flow.push --digest <id>` pushes `develop` + `main` + new tags atomically, then extracts the package **at the tag** via `repo-extract` into `../packages/forge` — only committed tag content is exported. Before any extract runs, the `preflight-extract-gates` step (RFC-1517) refuses two source-derivable defect classes in milliseconds: a `CHANGELOG.md` at the ref without the `[<version>]` section being published (`FLOW-PUB-01` — write the section before publishing per the packages/AGENTS.md publish-order rule) and a shipped file's `../` path literal resolving outside the package root (`PKG-HEALTH-10`, reported at file:line — the same durable rule `forge.package.health` runs on routine checks). Both refusals leave `repo-extract` unspawned; the post-extract changelog gate below stays as defense in depth. Escapes for justified non-path literals: a same-line `// pkg-health-10: <reason>` comment (source files), or a `pkgHealth10Suppressions:` path list in `extract.config.yaml` for files that cannot carry comments (JSON) or whose literal sits inside a fixture string. Doc files (`.md`) and binaries are exempt — prose links are never resolved, and `tsconfig.json`/`package.json` literals rewritten or tolerated by repo-extract belong on the config list.
3. `hooks/extract-verify.sh` verifies the extract with `scripts/verify-extract.mjs` — the same script surface standalone CI runs (install, lint, typecheck, build:check, test, build) plus a changelog gate that requires a `[<version>]` section in `CHANGELOG.md`.
4. On a non-fast-forward rejection the push reconciles once with `merge -s ours` (the local tree stays the authoritative export) — never force-push. Retries are journal-scoped: rerun `flow.push` with the same digest and exactly the pushed-but-unpublished tags are published.
5. CI on GitHub picks up the push and publishes to npm automatically.

**Do NOT invoke `repo-extract` directly for releases** — it bypasses verification and the clean-source contract.

After CI completes, verify the new version on [npmjs.com/package/@warpgogol/forge](https://www.npmjs.com/package/@warpgogol/forge).

## Version

The version in `packages/forge/package.json` is the source of truth. Do NOT set `versionBump` in `extract.config.yaml` — `repo-extract` applies it on top of the monorepo version, causing auto-increment on every extract.

## publishConfig

`publishConfig` in `package.json` overrides local exports with `dist/` paths during `npm publish`. The `dist/` directory is built by CI before publishing.

## CI

The CI workflow is generated by `repo-extract` from `generateCiWorkflow` in `packages/repo-extract/src/fs/transform.ts`. Changes to the embedded `.github/workflows/ci.yml` are overwritten on the next extraction — edit the generator, not the embedded file.
