# @warpgogol/forge Agent Guide

Portable governance skills and command modules extracted from the engine (RFC-0374) (RFC-0374).

## Architecture

- `src/` — portable, no kernel imports. Contains skill schema, registry, validators, onboarding handlers, config module, canonical types, and utilities.
- `os/` — ForgeModule registrations. RFC-0556: `os/compass/` and `os/werkstatt/` are fully autonomous — all command handlers are inlined in `os/*/handlers/` and no longer dynamically import `@warpgogol/*` packages. Other `os/` modules may still use dynamic imports where kernel integration is needed. RFC-0940: all `os/*.module.ts` files declare a required `runtime` field (`"autonomous"` or `"werkstatt-adapter"`). Only `os/werkstatt/` may import `@warpgogol/werkstatt-engine` — all other `os/` directories are autonomous. ADR-0019: `@warpgogol/werkstatt-shared` is no longer a dependency — `scanDirectoryForImports` is inlined in `os/core/handlers/forge-autonomy-validate.ts`. `forge.autonomy.validate` enforces FORGE-AUTONOMY-01. Type-only imports (`import type`) are exempt. 2026-09-22: the `@warpgogol/werkstatt-engine` devDependency was removed from `package.json` to break the turbo-reported forge↔engine package cycle — `os/werkstatt/handlers/workspace-deps.ts` now bridges fingerprinting via `@warpgogol/werkstatt-shared/fingerprint` (canonical home since RFC-1104). Do not re-add an engine dependency; new bridge needs go through `werkstatt-shared` subpaths.
- **Forge helpers accept `io?: WorkspaceIO` as an OPTIONAL type-only parameter** (`import type { WorkspaceIO } from "@warpgogol/werkstatt-shared/kernel/workspace-io"`). Agents MUST NOT import `createDefaultIO` or any runtime binding from `@warpgogol/werkstatt-shared` into `packages/forge/src` — FORGE-AUTONOMY-01 (ADR-0019) exempts `import type` only. The ambient path stays the default for the standalone CLI; kernel callers pass `context.io` explicitly so operations flow through the recording adapter. First application: `writeFileIfChanged` in `src/utils/fs-idempotent.ts` (RFC-1149 follow-up, 2026-09-25).
- `bin/` — CLI entrypoint (`forge` command) for autonomous usage without `@warpgogol/werkstatt-engine`. **New `os/` modules MUST be registered manually in `bin/cli.ts` `buildRegistry()`** — the standalone CLI has no module auto-discovery. A module exported via `package.json` and wired in `tools/kernel.config.ts` profiles is still invisible to `forge <cmd>` until added to the registry array. Discovered 2026-09-16: `forge-adr` (and 6 other modules) existed in source but were unreachable via the CLI.
- `skills/` — forge-managed skill definitions (30 fo skills + 5 shared + 3 meta = 38 skills). Project-declared skill packs (RFC-0539) live outside forge and are discovered via `discoverPackSkills` from `forge.yaml` `skillPacks` config.
- **`skills/**` is the canonical source; `.agents/skills/**` is a byte-identical runtime twin** enforced by `src/tests/skill-agents-sync.test.ts` (written by `forge.init`/`forge.upgrade`). Edit the canonical file — never edit `.agents/skills/` directly. `ecosystem.commit`'s CHANGE_SUMMARY injection (RFC-1095) rewrites canonical bytes at commit time, and RFC-1435 rewrites each injected canonical's `.agents` twin byte-identically inside the SAME commit — agents MUST NOT hand-copy twins after a skill-touching governed commit (the commit carries both sides; a manual copy afterwards is a no-op at best and a stray diff at worst). A commit without a governance id injects nothing; stage an already-drifted twin alongside its canonical to resync it.

## RFC-0855 program control-plane boundary

Packet 000 will add the portable `forge/program@1` control plane under `os/program/` as specified by accepted RFC-0856 and its committed implementation plan. Do not implement it, register commands, or alter packet state before packet 000 is sealed. The module validates and writes governance artifacts only: it never executes packet work, commits, materializes decisions without a preparation lease, deploys, or imports `@warpgogol/werkstatt-engine`. Keep it cross-platform, deny unknown fields and unsafe paths, store only lease-token digests, and preserve packet 000 as the sole irreversible bootstrap.

Module notes:

`trajectory.index` extracts procedure units from green-verified sessions only (admission at extraction, bound to resolvable verdict artifacts — a verdict invalidated post-admission drops the unit at rebuild, TRAJ-04); `trajectory.recall` returns top-k situation-matched procedures at decision points (journaled for marginal-utility measurement), distinguishing a missing index (TRAJ-01) from an empty/stale one (TRAJ-02, basename `sourceWatermark` vs session filenames); `trajectory.outcome.record --helped|--hurt` feeds utilityScore + per-producer trust bucketed by `{workshopId, sessionClass}` so vendored units score under their origin's bucket. Units live in `docs/.index/trajectory/` (gitignored projection); recall/outcome history is append-only `recalls.jsonl`/`outcomes.jsonl` (YAML journals retired as write targets, lazy-migrated; a truncated tail drops only the partial record, TRAJ-06); `--export` emits a `forge/trajectory-shard@1` for cross-workshop vending.

`context.index.build` rebuilds `docs/.index/context/index.yaml` — a pure-projection unit catalog (session blocks, K-entries, frictions, remediation, RFC/ADR headers, skill manifests, handoffs, decisions). `context.assemble --task "<desc>"` emits a budgeted slate ranked by lexical + recency + path-overlap channels (dense slot declared, lexical-only floor shipped); `context.slate.eval` reports recall@budget over `docs/context-devset/`.

Every evaluated rule is journaled by the kernel executor into `docs/.index/checks/counters.jsonl` (append-only `{runId, ruleId, contract, outcome, at}`; `runId` reuses `commandInvocationId`; outcomes `pass|diagnostic|skipped|ensured`; suppressed under `--dry-run`; append failures warn, never fail — RFC-1474). `checks.counters.validate` audits the journal against `docs/validator-inventory.generated.yaml` (COUNT-01 unknown contract/rule or malformed record, COUNT-02 non-monotonic append order). `checks.counters.export` projects per-rule totals (`evaluated`/`diagnostic`/`lastRunId`/`lastAt`) into `docs/metrics/check-counters.generated.yaml` with deterministic `generatedAt` = max journal `at` (COUNT-03 freshness; a producer's own appended tail is tolerated).

`checks.contribution.report` uses the counters journal as the canonical firing source — `effectiveCoverage` is real coverage (`none|partial|complete`; CONTRIB-03 flags an absent/empty journal), session sidecars remain the secondary signature/diagnostic-history source — and classifies each gate-catalog rule `earning|silent|redundant|guard` with a recommended action (`probe`/`scope`/`retire-rfc`/`keep`); the report lands at `docs/metrics/check-contribution.generated.yaml`.

`session.audit` runs deterministic Stage-A detectors over `docs/sessions/*.md` + `archive/` — AUDIT-01/02 coverage caveats (.raw present, --deep without modelBinding), AUDIT-10 circumvention (denied gate → bypass route), AUDIT-11 blocker deception, AUDIT-12 generated-file edit, AUDIT-13 denied retry, AUDIT-14 false completion claim — and writes `docs/sessions/audit/<id>.audit.yaml` sidecars (deterministic `auditedAt` = session date). `session.audit.report` aggregates the sidecars into `docs/metrics/session-audit.generated.yaml` + links finding classes to frictions.

`gate.probe` injects `docs/gate-probes/<contract>/<rule>/fixture.yaml` at its real workspace path (backup → invoke → restore) and proves the bound check still fires on its seeded violation — a silent pass is a dead gate. `gate.probe.catalog` reports per-contract coverage + unprobed error-severity rules.

## Fixed branch model (RFC-1486)

- Branch classes: protected `develop`/`main`, and conforming `auto/<kind>-<YYMMDD>-<NN>-<slug>` where `kind` is `task|session|fix`, `YYMMDD` a real UTC calendar date, `NN` a 01–99 sequence, and `slug` lowercase alphanumeric words joined by single hyphens (3–48 chars).
- `flow.check` audits the checkout (FLOW-01..05): stray local branches, missing `develop`, guard absent or drifting from the shipped asset, `main` commits absent from `develop` (warning), malformed `forge.generated.yaml`. `flow.install` plans and executes adoption — creates/fast-forwards `develop`, pins `core.hooksPath` to `hooks`, installs the guard, and lands one adoption commit.
- The guard is portable POSIX `sh` at `os/flow/assets/flow-guard.sh`, installed byte-identically as `hooks/flow-guard.sh` plus a managed `pre-commit` block. It refuses direct commits on protected `develop`/`main` (FLOW-GUARD-01), branch names outside the grammar (FLOW-GUARD-02), commits on a detached HEAD outside a rebase or cherry-pick (FLOW-GUARD-03), and a `FORGE_FLOW_OP` value outside the closed vocabulary (FLOW-GUARD-04).
- Only Forge flow commands set `FORGE_FLOW_OP`. Agents never set it manually, never commit with `--no-verify`, and never hand-edit the managed hook block — repair goes through `flow.install`.
- A repo with a valid `forge.generated.yaml` (`schema: forge/generated@1`) is exempt from the model; an invalid marker is an error, never an exemption. Repos without `forge.yaml` are ungoverned.
- The model is dormant until the wave-4 switch-over — shipping the module does not adopt this or any other repository.

### Release lines (RFC-1488)

- Two release line kinds carry versions: the repository line (tag prefix `v`, root `package.json`) and one package line per workspace-glob directory containing `extract.config.yaml` (tag prefix `<dir-basename>@`). Directory basenames must be unique across release lines — collisions are FLOW-VER-02.
- Tag shapes are `vX.Y.Z` (repository) and `<package>@X.Y.Z` (packages) — annotated tags only, strict three-integer versions; lightweight tags and non-matching names are invisible to a line. A line's last release is the semantically highest reachable tag, never the nearest.
- `flow.version` is read-only (`--line <id>` optional, unknown id → FLOW-VER-04): last tag, current version-file value, commits since the tag under the line's paths, and the derived version `X.Y.Z+N.<9-char-head>` (`.dirty` when the line's paths carry tracked modifications; the tag version itself when N=0; `null` plus FLOW-VER-01 when the line was never baselined).
- The pending level comes from `X-RFC` commit trailers resolved through the canonical RFC reader (`forge.yaml` `resolverDoors.rfc`): each referenced RFC's `versionBump` contributes its level, `patch` is the floor for any commit, `none` only when no commit touched the line. A missing RFC file counts patch with FLOW-VER-03.
- No version file is edited between releases — a version value diverging from the line's last tag is FLOW-08 (error), and an `extract.config.yaml` declaring `versionBump` is FLOW-09 (repo-extract would rewrite it on export).
- Tags are created by exactly two writers: `flow.install`'s baseline step (level `baseline`, at the commit that introduced the version, only when the version file outranks the last tag and that commit is on `main` — FLOW-ADOPT-07 refuses backwards or off-main baselines) and the wave-2 release cut. Agents never create release tags by hand.

### Session worktrees (RFC-1487)

- `flow.open --kind session --slug <slug>` branches `auto/session-<YYMMDD>-<NN>-<slug>` off `develop` into a sibling worktree `<parent>/<repo>@auto-session-<YYMMDD>-<NN>-<slug>` (NN = next free daily sequence across local and remote-tracking refs) and registers it in `<git-common-dir>/forge/registry.yaml` — shared across all worktrees of the repo.
- `flow.integrate --branch <name>` holds `forge/integrate.lock` from rebase through fast-forward: rebases the branch onto `develop` (conflict → FLOW-INT-02, branch left intact), runs the **primary checkout's** `hooks/integration-gate.sh` with the branch worktree as cwd (a session cannot weaken its own gate — FLOW-INT-05), verifies the primary is clean and on `develop` (FLOW-INT-06/07), then `git merge --ff-only`s and cleans up; reruns after a partial cleanup resume without moving `develop` again.
- `flow.discard --branch <name> --reason <text>` removes a registered branch's worktree, ref, and registry entry — refuses on dirty worktrees (FLOW-DIS-02), held entries, or a missing `--reason`. `flow.status` reports the primary state plus per-branch registration, presence, dirty counts, ahead/behind, and 72 h staleness — read-only, creates no `forge/` state.
- `flow.check` adds FLOW-06 (unregistered `auto/*` branch stale > 72 h, warning) and FLOW-07 (registry/git disagreement — registered branch or worktree missing, stale journal metadata; schema-invalid registry is error severity).
- `forge/registry.yaml`, `forge/journal.jsonl`, and `forge/*.lock` are machine-owned — agents never edit them by hand; only flow commands write them. The lifecycle activates with the wave-4 switch-over RFC.
- **A dirty-check gate must use the same dirt definition as the git operation it predicts.** `git worktree remove` refuses on untracked files; `git merge --ff-only` ignores them (unless one collides with incoming content). `statusDirty` (full porcelain) predicts removal for session worktrees (FLOW-INT-01, FLOW-DIS-03, per-branch dirty counts); `statusTracked` (`--untracked-files=no`) predicts merge-ability for the primary (FLOW-INT-03, `primary.clean`) and drives `flow.version`'s `.dirty` suffix, whose contract is tracked-only. Discovered during the RFC-1487 review: a tracked-only gate green-lit an untracked-only worktree, moved `develop`, then failed `worktree remove` mid-cleanup.

### Releases (RFC-1490)

- `flow.cut [--lines <id,…>]` is the ordinary release: it opens `auto/session-…-release-<ver>` through the normal open path (owner `release`), writes versions via verified JSON-equal replacements (FLOW-CUT-11), lands `chore(release): <tag>[, <tag>…]` into `develop` under the integration lock + gate, collects `hooks/release-fingerprints.sh` output (flat YAML string map → FLOW-CUT-08), compare-and-swaps `main` to the `develop` tip, and writes `forge/release-tag@1` annotated tags — repository line always, package lines only via `--lines`. A `major` level requires `ALLOW_MAJOR_BUMP=1` (FLOW-CUT-05). Reruns resume from the tip's `chore(release):` subject — all named tags present reports `released` with no mutation, missing ones complete the tail.
- `flow.fix --slug <slug>` opens `auto/fix-…` at the `main` tip (`kind: fix`, `base: main`) — only when `main` sits exactly on the repository line's last-tag commit (FLOW-FIX-02) and no back-merge is owed (FLOW-FIX-04, so two fixes never stack two ports). `flow.cut` inside that worktree (or `--branch <fix branch>`) ships a **patch-only** release: `--lines` is forbidden (FLOW-CUT-09, touched lines come from `git diff baseSha..fixTip`), minor/major trailers refuse FLOW-CUT-10, the gate runs with `FORGE_FLOW_TARGET=main`, `update-ref refs/heads/main` is atomic, and the back-merge follows immediately — a conflict still reports `released: true` with `backmerge: "conflict"` and the port worktree path.
- `flow.backmerge [--redo]` ports `main` into `develop` through `auto/session-…-port-<first-tag>` — **always** a merge commit, even when the merge is clean. The fixed message is `release <tag>[, <tag>…] → develop`; `flow.integrate` on the port verifies that message plus second parent `port.mainSha` (FLOW-INT-09) and that `develop` never moved since the port opened (FLOW-INT-10 → `--redo`). A conflicted port merge stays in progress — resolve in the port worktree, `git commit --no-edit`, then `flow.integrate`.
- `flow.install` also installs `hooks/pre-merge-commit` (managed block → `flow-guard.sh pre-merge-commit`); `pre-merge-commit` accepts **no** `FORGE_FLOW_OP`, so a manual merge commit on `develop`/`main` is FLOW-GUARD-01 — the only merge commits the model allows are forge-made port merges on `auto/*`. `FORGE_FLOW_OP=backmerge` no longer exists (amends RFC-1486); Forge commits instead carry informational `FORGE_FLOW_COMMIT` (`install|cut|backmerge`, `hold` reserved for the outbound RFC) which the guard never reads.
- The dirty-tagged derived version is `X.Y.Z+0.<9-hex>.dirty` — every `flow.version` value is valid semver.

## Golden contract conformance (RFC-1365, DNA-115)

- A repository that emits a versioned contract bundle for an external authoritative consumer MUST declare the producer in `contractProducers[]` in `forge.yaml` and wire a golden-conformance run through the consumer's real validator — `forge.conformance.run` (emit → mirror → consumer legs over `src/conformance/index.ts`) plus `forge.conformance.validate` (CONF-01..06 lint). The `@warpgogol/forge/conformance` subpath export exposes the same execution path to producer vitest suites.
- An absent `consumer.root` self-skips by default; `--require-consumer` or `FORGE_CONFORMANCE_REQUIRE=1` fails closed where the checkout is guaranteed.
- Naming disambiguation: golden _contract_ conformance (this) ≠ DNA-78 component-runtime conformance ≠ DNA-61 content golden baseline ≠ verbund fixture conformance.

## RFC-1053: Skill effectiveness metrics

`metrics.aggregate` (RFC-1053) queries and aggregates per-skill effectiveness metrics from `docs/metrics/` YAML files. Metrics are generated at two integration points:

- `rfc.implement.stamp` — generates `docs/metrics/rfcs/<rfc-id>.metrics.yaml` after successful stamp (non-fatal on failure).
- `session.save` — generates `docs/metrics/sessions/<session-id>.metrics.yaml` from parsed ATIF messages (non-fatal on failure).

Both generators are best-effort: metrics failures log a warning and never block the primary operation. Agents MUST NOT manually edit `docs/metrics/` files — they are generated artifacts produced by `rfc.implement.stamp` and `session.save`.

## Compass contract extension points (RFC-0943)

Skill packs MAY declare additional Compass contract blocks beyond the built-in `MODULE_CONTRACT`, `KEY_DECISIONS`, and `CHANGE_SUMMARY` (v2, RFC-1094) via `forge.plugin.yaml` `extensionPoints.compass.contract.blocks[]`. Each block spec is declarative data:

- `blockId` — kebab-case identifier (e.g. `api-contract`). The marker in source files is the uppercased, underscore-separated form (e.g. `<API_CONTRACT>`).
- `requiredFor` — glob patterns matching files that must carry this block (e.g. `["packages/my-pack/**/*.ts"]`).
- `requiredTags` — optional array of `{ name, minWords? }` tags that must appear inside the block.

`compass.validate` loads block specs from all declared skill packs via `loadContractRegistry` and emits `COMPASS-PLUGIN-01` (missing block), `COMPASS-PLUGIN-02` (missing required tag), and `COMPASS-PLUGIN-03` (tag below minWords) diagnostics. Duplicate `blockId` across packs is rejected with `COMPASS-PLUGIN-DUP-01`. The `FORBIDDEN_PATTERNS` negative list stays hardcoded in `compass-inventory.ts` and is not extensible by packs.

## Compass policy externalization (RFC-1096)

All Compass policy values — scan roots, file extensions, ignored dirs/prefixes, test patterns, high-risk globs, layer/risk rules, workspace-kind map, exclusion globs, governance-ID and boilerplate regexes — are resolved by `resolveCompassPolicy` in `os/compass/policy.ts` from three layers: generic defaults → stack profile `compass:` section → consumer `forge.yaml` `bindings.compass`. Agents MUST NOT add stack- or consumer-specific literals (paths, extensions, regexes) to `os/compass/**` — they belong in `profiles/*.yaml` or the consumer's `forge.yaml`. Union keys merge with `!`-subtraction; `scanRoots`, `idPattern`, `purposeBoilerplatePatterns`, `layerRules`, `workspaceKinds` replace wholesale. `idPattern` must match the `ABC-123` probe or resolution throws `CompassPolicyConfigError`. See `docs/reference/forge-yaml.md` `bindings.compass` for the key reference.

Exclusion, layer, and risk globs match `relativePathWithinWorkspace`, not the repo-root-relative path. For leaf-workspace scans (`--workpiece`, `--site`, or a cwd-resolved site) it is computed relative to `scanRoot` (the workpiece/site dir); for `--packages`, `--package`, and default `scanRoots` it is repo-relative with the workspace-kind prefix stripped via `getWorkspaceRelativeSegments`. Author exclusion globs (e.g. `public/_video/**`) against the workspace-relative form — a repo-relative glob silently fails to match leaf scans. See `createCompassInventoryEntries` in `os/compass/handlers/compass-inventory.ts`.

## Commit and config loading rules

- **Verify `ecosystem.commit` output.** `ecosystem.commit` commits whatever is in the git index (staged files). If another agent staged files before your call, those files will be included in your commit instead of your own. After every `ecosystem.commit`, run `git show --stat HEAD` to verify the correct files were committed. If wrong files were committed, the missing files remain untracked/unstaged and must be committed separately.
- **The git index is shared mutable state across parallel agent sessions.** `ecosystem.commit` commits the whole index — a parallel session's commit can sweep YOUR staged files into their commit (wrong message), and their `git reset` can silently drop your stage. Stage immediately before `ecosystem.commit` inside the same shell command, then verify `git show --stat HEAD`. Discovered during RFC-1153: implementation files were swept into a parallel RFC-1154 commit — content landed correctly, commit boundaries were dirty.
- **Take over a dead background agent by verifying its file state, not its report.** A subagent killed mid-flight (rate limit, crash, timeout) leaves partially applied edits and no reliable completion signal — its final message may describe work that never landed. Before building on its work: `git status` + `git diff` every declared path to see which edits actually landed, then compile the touched package — a clean typecheck is the cheapest completeness signal, and a parse/type error locates the truncation point. Then either complete the remaining spec or revert the partial edits first. Discovered during session-20261030-0014 (F-0034): an implementation agent died mid-edit and the takeover had to map which hunks had landed before writing a line.
- **Verify a friction's `addressed` artifact contains the fix, and commit rule edits immediately.** `friction.validate` checks that `artifacts[]` paths exist — not that the rule text landed. An uncommitted AGENTS.md edit can be silently reverted by a parallel agent's stash-sweep/merge cycle (a gate-isolation stash restoring around your edit can merge or drop it). Before flipping `status: addressed`, grep the file for the rule's key phrase; commit rule edits the moment they land. Discovered during session-20261030-1030 (F-0035): the F-0034 takeover rule was marked addressed while absent from the file.
- **Dedupe after a stash-restore merge before committing.** `ecosystem.commit`'s gate-isolation restore merges swept edits back — a parallel rewrite of the same file mid-window produces a real merge that retains BOTH versions, leaving near-duplicate bullets. After an EC-26 recovery or a restore that touched shared files, diff the result for duplicated rules/tests before committing. Discovered during RFC-1443: the self-gate merge left two takeover bullets in this file.
- **Friction `artifacts[]` paths under `docs/rfcs`, `docs/plans`, or `docs/audits` go stale when `docs.archive` moves terminal documents.** Update them to `archive/<status>/` paths in the same commit as the archive move — `friction.validate` (FRICTION-05) flags the stale path on the next run. Discovered during session-20261030-1030: F-0011's RFC-1435 artifact broke on archive; F-0032's was repaired preemptively.
- **Escalation ladder (RFC-1460): a recurring docs-rule scar must climb to a mechanical measure, not accrete prose.** The ladder is `docs-rule → skill-step → validator | code-change | flag-default | pipeline`; one step up per recurrence is allowed, two recurrences on the same rung require a bigger step. An `addressed` entry whose signature recurred 2+ times on a docs-only measure is FRICTION-06 — flip it to `status: escalated`, keep `measure` naming the mechanical obligation (RFC/ADR id, docs/queues item, repo path, or backticked command token; FRICTION-08), and never append a second docs-rule measure. `docs-rule` stays the *first* measure for a fresh friction — escalation applies only after empirical failure; `escalated` is a holding state that returns to `addressed` when the mechanism lands, never a fallback for missing mechanisms (`external` covers outside-the-repo fixes).
- **The platform-scope commit guard checks the files in the commit, not the whole index.** `git commit` is blocked only when the commit's own file set touches `packages/**`/`integrations/**`/`services/**` — a docs-only `git commit -- <docs paths>` (pathspec commit) passes even while foreign platform files sit staged, and leaves their stage intact. Use this for docs-scope commits when the index holds someone else's platform work; platform-scope files of yours must still go through `ecosystem.commit` (which sweeps the whole index — coordinate or wait). **Pathspec commits fail on untracked paths** — `git commit -o -- <paths>` reports "pathspec did not match" for `??` files; `git add` the new files first, then the same `-o` commit takes only the listed paths. Discovered during the 2026-10-12 session-end: archive moves committed cleanly via pathspec while a parallel session's engine changes were staged; untracked-path failure hit during RFC-1308 evidence commit.
- **`ecosystem.commit` splits a mixed-scope change into TWO commits — pick the code-bearing one for `--implementation-commit`.** A file set spanning platform (`packages/**`) and non-platform (`docs/**`) paths lands as a platform commit (version bump) plus a same-message docs commit; `STAMP-GOV-01` scans whatever SHA you pass, so `git log --grep` on the message returns either half. Verify with `git show --name-only <sha>` that the commit carries the implementation files before stamping. Discovered during RFC-1437 stamping: the docs half failed provenance scan while the platform half was correct.
- **A file commits wholesale — you cannot split one file's hunks across two RFC commits.** When a sibling agent's in-flight edits share your file, either let your hunk ride inside their commit (note attribution in the review report) or revert-and-reapply after they land. Discovered during the RFC-1436/1437 fix-forward: a footer review fix deferred one commit to keep attribution clean.
- **Wrap `loadForgeConfig` in try/catch in handlers that run in test workspaces.** `loadForgeConfig` throws when `forge.yaml` does not exist at the workspace root. Handlers that may be called from test workspaces without a `forge.yaml` (e.g. `runCompassValidation`) must guard the call with try/catch and skip pack-dependent logic when config is unavailable.
- **Read a data file's real shape before writing its parser — an invented field name produces a structurally dead join that passes the fixture and fails every review.** The validator inventory uses `contract:` not `name:`; `docs/frictions.yaml` is a bare top-level sequence, not `{frictions: [...]}`; `SessionFrontmatter` carries `files`/`types`, not `filesChanged`/`taskKind`; the command manifest serializes per-command flag specs, not a `rules[]` array. `head` the real corpus file or grep the canonical parser's schema before asserting on a fixture — discovered during RFC-1469/1471/1472/1473 review rounds where invented shapes made every firing join dead.
- **Generated artifacts derive timestamp fields from source data, never `new Date()`.** A wall-clock `generatedAt`/`auditedAt` makes the `--check` staleness comparison permanently fail on the next emit — derive the timestamp from the max in-window source value (session frontmatter `date`, sidecar `auditedAt`, max source `completedAt`). Discovered during RFC-1471 (`auditedAt`) and RFC-1473 (`generatedAt`).
- **The `X-RFC` trailer only lands on version-bump commits — a queue of `--skip-bump` fix rounds leaves `rfc.implement.stamp` with no provenance to scan.** When the stamp fails STAMP-GOV-01 on a fully implemented RFC, `git commit --amend -m "<subject>" -m "X-RFC: <id>"` the tip commit before stamping. Discovered during RFC-1471 and RFC-1472 stamping.
- **Archive listers return paths relative to the archive dir — merge active+archive lists with their `{base, prefix}` tagged, and emit `${prefix}/${rel}` for provenance.** A bare `docs/<dir>/${rel}` produces dead citations for every archived item. Discovered during RFC-1471 (archive sessions silently skipped) and RFC-1472 (445 units cited a non-existent path).
- **Splitting a test file trims imports to the handler under test.** When an AC-required split moves shared-header imports into each new file, only the handler the file exercises stays imported — the lint gate rejects the commit on unused symbols. Run scoped lint before `ecosystem.commit`, not after it rejects. Discovered during RFC-1470 and RFC-1472 test splits.
- **Verify the write target path immediately before every edit.** A stale path variable or a wrong `file_path` writes handler code into an unrelated file — the corruption costs a git-restore + re-apply cycle. The tool's `file_path` is the contract; check it names the file you intend, then write. Discovered during RFC-1471's r1 repair (`session.module.ts` corrupted by a report-handler edit).
- **A `forge.yaml` fixture missing `paths:` silently degrades to generic Compass policy.** `loadForgeConfig` schema-validates the whole file — a minimal fixture without the required `paths:` section fails validation, `resolveCompassPolicy` falls back to generic defaults, and custom `bindings.compass.idPattern` values are never read (custom-format tokens get filtered out with no error). Always include `paths:` in forge.yaml test fixtures; for Compass tests use the shared `os/compass/handlers/tests/forge-yaml-fixture.ts` (`forgeYaml` / `writeForgeYaml` / `policyWithIdPattern`) instead of copying YAML strings. Discovered during RFC-1220: contract tests silently dropped mission-format history tokens until the fixture gained `paths:`.
- **Vitest `describe.runIf`/`skipIf` still executes the describe callback during collection.** Only the `it` bodies are skipped — initializers at describe-body level (e.g. `loadForgeConfig`) run unconditionally and will throw. Guard the initializer itself (`cond ? loadForgeConfig(...) : null`) so collection survives the missing precondition. Discovered during the 5.3.0 export: `skill-agents-sync.test.ts` threw on standalone CI even though the suite was correctly marked skip.
- **`ecosystem.commit` scoped tests run with cwd inside the package dir, not the repo root.** `vitest run` under scoped-tests executes with `process.cwd() === packages/<pkg>` — tests that resolve workspace paths from `process.cwd()` (e.g. `resolveForgeRoot(process.cwd())` expecting `packages/forge` below it) must tolerate both layouts or compute paths independently of cwd. Discovered during RFC-1225: an AC test asserting `resolveForgeRoot(root) === root/packages/forge` passed from the repo root but failed under the commit pipeline, where the fallback resolution returned the package dir itself.
- **`listStackProfiles` returns `[]` for a missing `profiles/` dir — it does not throw.** Distinguishing "catalog unavailable" from "catalog present but empty/unknown id" requires an explicit `existsSync` on the profiles directory. Discovered during RFC-1118: without the check, an unreadable catalog produced a spurious "unknown profile id" fail instead of "catalog-unavailable" warn.
- **`rfc.implement.stamp` enforces commit-time governance provenance (STAMP-GOV-01, RFC-1310).** The selected implementation commit — or one of its auto-detected candidates — must carry an `X-RFC: <id>` trailer or an injected `CHANGE_SUMMARY <item>` naming the id; a bare subject mention is a reference, not provenance. Implementation commits therefore land via `ecosystem.commit --rfc <id>` (see the `fo-idea-implement` commit template), and the same parity guards (COMMIT-GOV-01/02/03) apply at commit time — full rule text lives in `packages/AGENTS.md`.
- **Stamp evidence annotations are strict-grammar (STAMP-CHECK-01).** Every acceptance criterion must carry a resolvable `(evidence: …)` as its own parenthesized group — `(evidence: probe:AC-N)`, `(evidence: test:<path>)`, `(evidence: <path>:<line>)`. Nesting evidence inside a larger paren group (`(behavior; evidence: …)`) is not parsed. Probe `expectationSource` must be `self` when the probe was authored in the same session/implementation commit (RFC-IMP-10 derives self-authoredness from git, not from intent) — write `expectationSource: self` on all new probes instead of `requirement`/`independent`. Ordered stamp checklist: `verification.emit` → evidence annotations → `ecosystem.commit --rfc` implementation commit → `rfc.implement.stamp`. RFC-1483: the default invocation **self-repairs** the repairable prerequisite class — unchecked-but-evidenced criteria flip and a missing/stale envelope re-emits inside the atomic write (reported under `repaired[]`), so emit/annotation steps only need manual attention when the repair pass cannot satisfy them; `--no-repair` restores the blocking gate, and unrepairable failures print this checklist as ordered `violations[]` with `fixHint`. Discovered during RFC-1434 stamping (F-0009).
- **Fail-closed recovery of corrupted config fields requires the Zod schema to accept the corrupted shape.** Strict validation runs before any recovery logic — a schema that rejects the corrupted form makes recovery unreachable. Widen the field schema (e.g. `z.union([string, object])`), recover in `loadForgeConfig`, and heal on the next `serializeForgeConfig` write. Discovered during RFC-1118.
- **Register new top-level directories in `NAMING_CONVENTION_IGNORED_TOP_LEVEL`.** When a new top-level directory appears in the repo (e.g. `.adr-locks`, `.devin`, `.forge`, `.rfc-locks`, `patches`, `storage`), add it to `NAMING_CONVENTION_IGNORED_TOP_LEVEL` in `os/naming/naming-convention.ts`. Otherwise `naming.convention.lint` reports "unknown top-level directory" errors.
- **Add tool-generated/imported/historical dirs to `NAMING_CONVENTION_EXEMPT_DIRS`.** Directories containing tool-generated files (e.g. `docs/performance` with timestamp-based names), imported specification documents (e.g. `docs/specs` with `01-PBP-System-Specification.md`), and archived RFCs (e.g. `docs/rfcs/archive`) should be added to `NAMING_CONVENTION_EXEMPT_DIRS` in `os/naming/naming-convention.ts` to avoid false-positive kebab-case violations on files whose naming is controlled by external tools or conventions.
- **Use `%s` not `%B` for git log delimiter parsing.** When parsing `git log --format` output with `\x1f`-delimited fields, use `%s` (subject only) instead of `%B` (full body). `%B` includes newlines which break the per-line `split("\x1f")` parsing, causing all entries to be silently skipped. Discovered during RFC-1053 `metrics-rfc.ts` implementation.
- **`writeFileAtomic` does not create parent directories.** `src/utils/fs-atomic.ts` writes the temp file directly — a missing parent dir fails with ENOENT. Always `mkdir(dirname, { recursive: true })` before calling it for paths whose parent may not exist (e.g. `docs/` in a fresh workspace). Discovered during RFC-1139: `saveLedger` crashed on `docs/compass-audit-ledger.generated.yaml` in a test fixture without `docs/`.
- **Chicken-and-egg with self-referential acceptance probes.** When an RFC's acceptance probe checks for a file that is created by `rfc.implement.stamp` itself (e.g. `docs/metrics/rfcs/<rfc-id>.metrics.yaml`), `rfc.verification.emit` will always report "fail" before stamping because the file doesn't exist yet. Solution: generate the file manually first (e.g. via a node script calling the generator function), re-emit evidence, then stamp. The stamp's `RFC-IMP-06` check requires evidence to be "pass" before proceeding. Discovered during RFC-1053 stamping.
- **`rfc.acceptance.run` `reachable` probes recognize structural edges only.** Reachability derives from the generated command manifest: pipeline composition, invoker references, or a declared `coverage: <class>` with a non-empty `coverageNote` in the module metadata. An AGENTS.md mention or a documented `werkstatt run` invocation does not count as an edge — a top-level operator-facing command (one nothing else invokes or pipes) needs the coverage edge declared explicitly or the probe reports it unreachable. Discovered during RFC-1349: `contract.ripple.apply` failed its `reachable` probe until `coverage: "operator"` + `coverageNote` were restored in `contract.module.ts`.
- **Check `batch:` frontmatter before creating sibling RFCs.** When an RFC references sibling RFCs (e.g. "the sibling lifecycle RFC"), grep `docs/rfcs/` for the shared `batch:` field first — the batch may already be fully drafted. Creating a new RFC for an already-drafted sibling produces duplicates. Discovered during RFC-1094 retro: RFC-1095/1096/1097 existed as drafts before the operator asked to "write the needed RFCs".
- **Mark forward references to unimplemented commands.** When documentation (skill templates, AGENTS.md, RFCs) references a command that does not exist yet — e.g. a sibling-RFC command like `compass.migrate` — mark it explicitly as `(sibling RFC, not yet implemented)`. Bare references make agents try to run non-existent commands. Discovered during RFC-1094.
- **Compass test fixtures must not embed literal contract blocks or banned literals.** `compass.summary.record` rewrites `<CHANGE_SUMMARY>` blocks found in a file's header region at commit time — a literal block inside a test file gets self-rewritten (this broke `compass-v2-contract.test.ts`). Build tags via concatenation (`"<" + "CHANGE_SUMMARY>"`) and construct banned literals dynamically so AC-4-style source scans do not flag the test file itself. Discovered during RFC-1096.
- **A containment/escape fixture must actually escape the asserted root.** A test asserting "writes cannot leave the workspace" is vacuous when the fixture's redirect target still resolves inside the workspace — the command passes legitimately and the test reports a false defect. Realpath the fixture target outside the protected root (e.g. `mkdtemp` under `os.tmpdir()`, not under the fixture workspace) and assert on the outside path. Discovered during the RFC-1481 review fix pass: a symlinked nested destination pointed at a dir inside the same workspace, so the resolver's correct `pass` read as a bug until the target moved outside.
- **Keep consumer/stack literals out of commit messages for `os/compass` files.** `compass.summary.record` embeds the commit message into `<CHANGE_SUMMARY>` items — verbatim minus git trailers and style-aware terminator neutralization (RFC-1233, RFC-1323: `*/` → `*∕` inside block comments, `-->` → `--›` / `<!--` → `‹!--` inside html comments, via `os/compass/comment-safety.ts`) — a message like "werkstatt-engine clean" lands the banned literal `werkstatt` inside `os/compass/**` sources and trips the AC-4 banned-literal scan (`compass-policy.test.ts`). Use generic package names in commit messages ("engine package clean") for commits that touch `os/compass` files. Authored `--text` (no `--injected`) carrying the target style's terminator is rejected with COMPASS-CS-08 — reword or escape; injected commit-message text neutralizes instead. Discovered during RFC-1097 sweep; contract finalized in RFC-1323.
- **AC evidence annotations must be bare file paths without em-dash suffixes.** `rfc.validate` (V-27) requires `(evidence: <file:line>)` or `(evidence: test: <path>)` annotations. The evidence parser treats everything after the prefix as a literal file path — adding descriptive text after an em-dash (e.g. `(evidence: test: packages/forge/src/tests/public-surface.test.ts — SURFACE-02 tests)`) causes "evidence references a file that does not exist" errors. Keep evidence annotations to `evidence: file: <path>` or `evidence: test: <path>` only. Discovered during RFC-1080 stamping.
- **`compass.validate` is workspace-scoped — in mission pipelines it scans `packages/*`, not just the workpiece.** `execute-pipeline` injects `--site` for workspace-scoped commands, but `resolveCompassScanRoot` still resolves the platform scan root (`scanRoots`/`packages/`) — so platform compass debt blocks site missions even when the workpiece itself is clean. To scan only the workpiece, run `compass.validate --workpiece <path>` directly. When a mission fails on compass errors in `packages/*`, fix the platform files — the workpiece is not the problem. Discovered during warpgogol-m000142: 170 platform violations blocked a 1-file workpiece mission.
- **`COMPASS-PURPOSE-02` requires a whole-word token match.** `deriveFileTokens` produces filename-stem segments, exported-symbol words, and (for generic stems like `index`/`helpers`) the parent directory name. The `<purpose>` text must contain at least one token as a standalone lowercase word — a camelCase symbol does not satisfy its own segments (`AuditService` does not satisfy `audit`). Write the token as a separate word in the purpose sentence. See `compass-inventory.ts` `deriveFileTokens` + the PURPOSE-02 check.
- **Always close `</MODULE_CONTRACT>`.** `extractBlockContent` matches `<TAG>...</TAG>` — without the closing tag the whole block is invisible to the validator, and `compass.validate` reports `COMPASS-CONTRACT-02`/`03` as if `purpose`/`non-goals` were missing. The diagnostic message does not mention the tag, so the missing closer is easy to overlook. When a sweep reports CONTRACT-02/03 on files whose `purpose`/`non-goals` visibly exist, check the `</MODULE_CONTRACT>` closer BEFORE editing content — one missing tag produces a cluster of phantom violations. Discovered during RFC-1154 (new files failed CONTRACT-02/03 until the closer was added); batch pattern confirmed during the 2026-09-27 sweep (8 files, 1 missing tag each).
- **Generators of committed artifacts must be idempotent.** Re-running a generator on the same inputs must produce byte-identical output — `spec.live.merge` guards on `history[]` (`already-merged` no-op, `--force` for surgical re-merge). Living-spec corruption (duplicated `(RFC-XXXX)` sections or `history[].rfc` entries — V-LS-06/V-LS-07 — and committed-content drift — V-LS-09) is repaired ONLY by `spec.live.rebuild`, never by hand-editing `docs/specs/live/*.md`; a V-LS-08 coverage gap (archived implemented `liveSpec` RFC absent from history) is repaired by `spec.live.merge --id <rfc>`. Kernel caveat: `--all` is consumed by `werkstatt run` as the site selector — commands that accept an all-* flag declare `acceptsAllFlag: true`, and the kernel injects `input.flags.all = true` into declaring handlers (RFC-1231); `kernel.flags.lint` flags a declared `all` without the gate (KERNEL-FLAG-09).
- **`compass.validate` has no `--files` flag.** The narrowest scope is `--package <name>` (leaf scans: `--workpiece <path>`, `--site <id>`). For post-edit checks use `--package forge --mode error` to skip debt the fix didn't touch. Discovered during RFC-1154.
- **Re-run `compass.validate` AFTER `ecosystem.commit`, not only before.** `compass.summary.record` (RFC-1095) appends a governance-ID item to every touched file's `CHANGE_SUMMARY` at commit time — a file collapsed to exactly the 5-item cap (CS-05) can be pushed back over the cap by the commit itself. Verify post-commit before declaring a sweep clean. Discovered during the 2026-09-27 compass sweep.
- **Package-metadata gates must model the exported artifact, not the source tree.** `repo-extract` generates `.github/workflows/ci.yml` from the `extract.config.yaml` `ci:` provider block and rewrites `package.json` — a check that requires an in-package `ci.yml` double-sources CI and flags every extractable package. Author package-health checks against what the export will contain (declared `ci:` provider OR embedded workflow), never only the monorepo file layout. Discovered 2026-10-10: PKG-HEALTH-02 flagged all 11 extractable packages until retuned to the generated-CI model.
- **The queue decision ledger's `stage` enum must track `PipelineStage` in lockstep.** `decisionEntrySchema` in `os/queue/types.ts` hardcodes its own `stage` list — when `src/pipeline-status.ts` `PipelineStage` gains a member (or a phase like `audit` is used for decision entries), extend the schema enum in the same change. A decision recorded on an unlisted stage makes the whole ledger unloadable: `queue.validate` fails schema validation on `items.N.stage`. Discovered during the RFC-1298..1300 session closeout: an audit-phase question (onboarding-w2 Q-4) was rejected until the enum gained `audit` (`decision-ledger.test.ts` covers all current members). Decision-window acceptance entries (`Accept RFC-XXXX?`) record `stage: plan` — there is no `resolution` member; prior queues use `plan` for the same question shape (session-20261030-0014 needed a schema repair after `stage: resolution` was written).
- **The decisions ledger requires `id`/`queue`/`createdAt` even when `items` is empty.** `docs/queues/<id>.decisions.yaml` fails QUEUE-01 on a hand-written minimal shape — the required top-level fields are `id: <queue-id>.decisions`, `queue: <queue-id>`, `createdAt: <ISO-8601>` (plus optional `baseline`, `policies`, `items: []`). Discovered during the ADR-0119 stamp run: a baseline-only ledger failed schema validation until the three fields were added.
- **Ledger `items[]` accepts only `Q-N` decision entries — run/progress records belong under a separate top-level key.** `decisionEntrySchema` requires `id: /^Q-\d+$/`, `doc`, `stage`, `question`, `resolutionPath`; progress notes like `kind: progress` inside `items[]` fail QUEUE-01 schema validation. The ledger's top-level object is non-strict — a `progress:` sibling key is tolerated (stripped on parse, preserved in the file) and keeps `items[]` clean. Discovered during the wave-1 closeout: per-RFC progress entries landed in `items[]` and the terminal `queue.validate` failed until they moved to `progress:`.
- **Attach an `error` handler before writing to a spawned child's `stdin`.** `execFile`-spawned processes can exit before draining stdin (e.g. `git cat-file --batch-check` in a non-git directory exits instantly) — the write then raises `EPIPE` on the stream, which surfaces as an unhandled-error crash, not a callback rejection. Swallow stdin errors (`child.stdin?.on("error", () => {})`) and let the execFile callback carry the real outcome. The race is scheduling-dependent — local runs pass while CI fails. Discovered during the forge 8.0.3 publish: `session.save` `extractCommitHashes` EPIPE-d CI's `pnpm test` despite green local runs; shipped in 8.0.4.
- **After `docs.archive`, re-check `git status` for unstaged source-path deletes.** The umbrella moves files in the worktree but does not stage them — staging only the `archive/**` destinations commits the adds while ` D` deletes at the old paths survive, splitting one logical move across two commits (and leaving a dirty tree that blocks `mission.reconcile`/`session.validate`). Stage with `git add -A docs/` (or add every source path explicitly) before `ecosystem.commit`. Discovered during the RFC-1444 session-end: the archive adds committed while the RFC's source-path delete stayed unstaged and needed a follow-up commit.

## Prettier compatibility and skill markers (RFC-1154)

Forge emitters produce prettier-normal output so consumer `prettier --check` passes without forge depending on prettier.

- **All markdown tables go through `alignMarkdownTable`** (`src/utils/markdown-table.ts`) — cells padded so `|` delimiters align per column, separator row is dashes repeated to column width (min 3). Never hand-emit `| --- |` literals; a regression guard test scans `src/**/*.ts`. `parseMarkdownTable` + re-emit is byte-stable (idempotency probe). Prettier's own table normalization differs in one detail: it inserts empty cells for missing trailing cells — our emitter does the same, so `align(parse(emit))` holds.
- **Managed `.prettierignore` block**: `applyPrettierignore`/`planPrettierignore` (`src/onboarding/prettierignore.ts`) reconcile a delimited block between `# forge-managed generated paths (RFC-1154)` and `# end forge-managed`. Content outside the markers is operator-owned and never touched. Unbalanced markers → the whole file is operator-owned (fresh block appended, no merge into a corrupt region). Detection is **root-only** (`prettier` in package.json deps or config key, a `.prettierrc*`/`prettier.config.*` at root, or an existing `.prettierignore`); nested-only configs are out of scope. Entries: per-skill `.agents/skills/<name>/` dirs carrying a `.forge-managed` marker, `**/*.generated.yaml`, `docs/sessions/`, `docs/metrics/`, `docs/queues/session-*.yaml`.
- **`.forge-managed` marker manifests** (`src/onboarding/skill-markers.ts`): every skill-sync site writes a JSON `{ files: string[] }` marker into each synced `.agents/skills/<name>/` dir, listing exactly what forge wrote (SKILL.md + knowledge files that stayed purely forge-content — merged/skipped files are excluded since they hold consumer entries). `pruneStaleSkillDirs` deletes a stale dir only when it carries a marker AND its on-disk contents are a subset of `manifest.files ∪ {marker}` — extra consumer files or a corrupt marker keep the dir and surface a warning. **Unmarked dirs are never pruned** (pre-1154 syncs, consumer-authored skills). Prune runs inside `reconcileGeneratedSurface` on every `forge upgrade` — including the same-version noop path — so stale syncs from deleted skills get cleaned.
- **`runInit` is sync; `runUpgrade` is async/io** — both paths wire the same contract via sync twins (`applyPrettierignoreSync`, `writeSkillMarkerSync`) vs the WorkspaceIO variants.

## Program packet control plane (RFC-0856)

The program packet control plane governs sequential packet execution under `forge/program@1`. It validates boundaries; it does not execute implementation commands or commit on behalf of agents.

- **Program Steward** and **Packet Executor** are distinct roles. A Steward seals packets, recovers stale leases, and validates completions. An Executor holds the lease and implements the packet. The same actor MUST NOT be both Steward and Executor for the same packet.
- **Manual state edits are forbidden.** Packet state transitions (`draft` → `sealed` → `active` → `completed`) must go through the registered commands. Self-sealing (a packet's Executor calling `seal` or `complete` for their own packet) is rejected.
- **Lease tokens are opaque and untracked.** Raw lease tokens exist only in memory and the command response. Only the SHA-256 hash is persisted in `.forge/program-leases/` (gitignored). Tokens never appear in tracked artifacts, logs, or completion reports.
- **Normative source hashes are exact-byte.** `normativeSources` in a packet record SHA-256 digests of the exact file bytes at seal time. Reordered YAML or reformatted JSON that changes byte content will fail validation, even if the parsed structure is semantically identical.
- **Bootstrap packet 000 is irreversible.** The `--bootstrap` flag on `program.packet.complete` is valid only for the first packet (no predecessor, program state `preparing`). It transitions the program to `executing`. There is no second bootstrap path.
- **Path validation is traversal-safe.** `allowedFiles` and `forbiddenFiles` use lexical path normalization that resolves `..` segments before glob matching, preventing directory traversal escapes.

## Archive convention

When archiving terminal artifacts, prefer the `docs.archive` umbrella command over individual `rfc.archive`, `adr.archive`, `plan.archive`, `audit.archive`, `session.archive`, `mission.archive` commands. The umbrella command runs all six in sequence and prevents leaving audits/plans/sessions/missions unarchived when the operator's intent is to clean up all terminal artifacts. Use individual commands only when the operator explicitly asks for a single domain (e.g. "archive only RFCs").

- **`plan.archive` never moves bare `plan-rfc-NNNN.md` files.** `extractRfcIdFromPlanFile` requires a `-<slug>` suffix after the digits (`/^plan-(rfc-\d{4})-/i`), so a slugless plan silently reports "skipped" — by convention these plans stay at `docs/plans/` root forever (plan-rfc-1335 does the same for a stamped-implemented RFC). Not a defect; do not rename or hand-move them. Discovered during RFC-1336 archival.

- **RFC-0711: `docs.archive` post-loop `spec.live.merge` step.** After archiving, `docs.archive` scans implemented RFCs with a `liveSpec` frontmatter field and calls `spec.live.merge` for each, creating or updating living feature specs under `docs/specs/live/<domain>.md`. Rejected RFCs with `liveSpec` are skipped. Merge failures are non-fatal — the archive step still completes; exit-nonzero or thrown merges are recorded in `results["spec.live.merge"].failed[]` (RFC-1235), never in `merged[]`, and print an error line in pretty output. Use `--dry-run` to preview merges without writing. Expect `docs/specs/live/*.md` modifications in the same dirty tree as archive moves — commit them together.

- **`rfc.validate --root <file>` does NOT scope validation to a single file.** It validates ALL RFCs in the repo regardless of the `--root` flag. To check specific RFCs, use `--json` with `2>/dev/null` (log lines go to stderr) and filter the `data.violations[]` array by `rfcId`. Discovered during RFC-1035–1038 gap analysis.
- **`rfc.archive` does NOT accept `--id`.** It archives ALL terminal-status RFCs at once. Available flags: `--dry-run` (preview), `--status <status>` (filter by status). Use `--dry-run` first to verify which files will move. Discovered during RFC-1038 archiving.
- **Post-archive follow-through repoints live references.** After `rfc.implement.stamp` + `docs.archive`, every live reference to the RFC's pre-archive path rots: repoint `<path>` in the RFC's `docs/knowledge-graph.xml` node(s) to `archive/<status>/`, and re-run `rfc.decision-log.generate` (the archive already refreshes `docs/rfcs/index.yaml` itself). Historical artifacts — review reports, decision ledgers, plans, sessions — keep the old path; do not rewrite them. `compass.docs.validate` is the verification gate for the repoint. Discovered during RFC-1307 archival.
- **Post-rename cleanup for `fs.rename` on watched directories:** When an archive handler uses `fs.rename` to move a directory that an IDE or file watcher is tracking (e.g. mission workpiece with an open `.astro/` cache), the watcher may recreate stale cache at the source path after the rename completes. Always add a post-rename cleanup check using `trashPath` from `utils/fs-trash.ts`: `if (existsSync(sourcePath)) { await trashPath(sourcePath); }` after the `fs.rename` call. See `os/mission/handlers/archive.ts` `moveMissionDir` for the reference implementation.

## Pinned-files protection (RFC-0733)

The pinned-files protection system prevents accidental deletion, move, or modification of foundational files (templates, configs, structural directories). It is opt-in — protection is active only when `.forge/pinned.yaml` exists.

- **`forge pinned.init`** creates `.forge/pinned.yaml` with default foundation entries, installs a pre-commit hook, adds `.forge/pinned-audit.log` to `.gitignore`, and optionally generates a CI workflow (`--ci`). Re-running merges defaults with existing entries — operator-removed default entries are re-added, but custom entries are never overwritten or removed.
- **`forge pinned.validate`** checks the working tree against the manifest. In `staged` mode (default), it checks `git diff --cached`; in `ci` mode (`--mode ci`), it checks the last-commit diff. Violations for `delete` and `move` operations are always blocked; `modify` is blocked only for `freeze` mode entries (not `protect`).
- **Override:** Use `--allow-pinned-override <path>` for an audited escape hatch. Each override is logged to `.forge/pinned-audit.log` (append-only, gitignored) with timestamp, path, mode, and reason. The `FORGE_PINNED_OVERRIDE` env var (comma-separated paths) is also read by `pinned.validate` — this allows the pre-commit hook to support overrides without changing the hook script: `FORGE_PINNED_OVERRIDE=docs/rfcs/rfc-0076.md git commit`.
- **Manifest integrity:** `pinned.validate` compares the current manifest against the last-committed version. If entries have been removed, it reports `PINNED_MANIFEST_TAMPERED`.
- **Archive pre-check:** All 6 archive handlers (`rfc.archive`, `adr.archive`, `plan.archive`, `audit.archive`, `session.archive`, `mission.archive`) load the pinned manifest once per invocation and skip pinned files/directories with a warning instead of moving them. When the manifest is missing, archive handlers behave as before (protection inactive). **Intra-directory moves are exempted:** if both source and destination are within the same pinned directory (e.g. `docs/rfcs/rfc-0076.md` → `docs/rfcs/archive/implemented/rfc-0076.md`), the move is allowed — the file hasn't left the protected directory.
- **`.forge/` directory:** The `.forge/` directory is a forge-specific convention for project-local governance files. It sits alongside `forge.yaml` and contains `pinned.yaml` (manifest) and `pinned-audit.log` (override audit trail).

## Agent-safety scripts in profiles (RFC-1019)

All Forge stack profiles include portable agent-safety scripts as embedded file content blocks. These scripts protect AI agents from destructive git operations and enforce session-end protocol.

- **`scripts/git-guard.sh`** — shell function intercepting `git stash`, `git reset --hard`, `git checkout --`, `git checkout -f`, `git switch -f`, `git clean -f`, `git restore`. Override: `ALLOW_DESTRUCTIVE_GIT=1`. Uses `FORGE_GIT_GUARD` marker (not `WERKSTATT_GIT_GUARD`).
- **`scripts/setup-git-guards.sh`** — auto-detects shell (zsh → `~/.zshenv`, bash → `~/.bashrc`) and installs git-guard.sh source line. Supports `install`, `--verify`, `--remove` modes.
- **`scripts/clean-stale-stashes.sh`** — detects and optionally drops stale git stash entries. Report mode (`--drop` to clean, `--drop-all` for all).
- **`scripts/check-clean-trees.sh`** — universal dirty-tree checker. Finds all `.git` directories up to 3 levels deep and checks each for dirty state.
- **`hooks/pre-user-prompt.sh`** — session-end protocol enforcement + stale-stash detection + git-guard verification. Requires `jq`. Exits with code 2 on session-end trigger phrases to inject protocol instructions.
- **`hooks/pre-user-prompt-wrapper.mjs`** — Node.js cross-platform wrapper called by `.windsurf/hooks.json`. Detects bash availability, prints one-time warning if bash not found (Windows without Git Bash), then delegates to `hooks/pre-user-prompt.sh`.
- **`.windsurf/hooks.json`** — Windsurf hook registration for `pre_user_prompt`, calls `node $ROOT_WORKSPACE_PATH/hooks/pre-user-prompt-wrapper.mjs`.
- **PREFERENCES.md** generated by `forge init` includes `formOfAddress` field and operational rules: plan confirmation vs implementation, skill invocation tracking, commit granularity, session-end protocol.

## Skills

Skills live in `skills/` and are synced to `.agents/skills/` by `create`. Each skill has a `SKILL.md` with standardized frontmatter (name, description, category, concerns, dependsOn).

- **When editing a skill in `packages/forge/skills/`**, the synced copy in `.agents/skills/<name>/SKILL.md` MUST also be committed in the same session — `create` is not run automatically after manual edits. Stale `.agents/skills/` copies cause `doctor` to report drift.
- **`compass.summary.record` rewrites the whole `CHANGE_SUMMARY` block canonically and collapses it to a 5-item window per file.** Staging an `.agents/skills/<name>/SKILL.md` mirror without its pack source in the same commit breaks byte-identity: the mirror receives the injected item plus a canonical re-wrap the source never got, and an over-cap item list collapses the oldest entry into `<history>` on the mirror only. Two safe shapes: commit mirror and source together (both get the same injection deterministically), or land a pure mirror resync with a governance-id-free commit message (no `--rfc`/`--adr` → `record` is skipped entirely). Discovered during RFC-1350 review: a mirror-only resync commit dropped `RFC-1307` from the mirror's item window while the source kept it.
- **Canonical sync path is flat**: `.agents/skills/<name>/SKILL.md` (e.g. `.agents/skills/fo-idea-implement/SKILL.md`). Both `create` (`init.ts`) and `upgrade` (`upgrade.ts`) sync to this flat path. A nested `.agents/skills/fo/<name>/SKILL.md` path is NOT created or maintained by forge — it is a stale artifact if present and should be removed.
- **After hand-editing a synced skill pair, verify byte-identity with `git diff --no-index <source> <mirror>`** — file-edit tools may normalize whitespace on write (e.g. collapse consecutive blank lines), silently diverging the mirror from the `packages/forge/skills/` source. Restore parity before committing; line-by-line `rtk diff` output is unreliable for pair comparison.
- **`FORGE_SKILLS[].path` is relative to the forge package root** and already includes the `skills/` prefix — resolve via `path.join(forgeRoot, skill.path)` (see `init.ts`). Never join a `skillsRoot` with `skill.path`: that produces a doubled `skills/skills/` prefix and silently finds nothing.
- **When renumbering steps in SKILL.md files** (inserting or removing a numbered step), grep for hard-coded step numbers across all `.md` files in the repo. Cross-references to `fo-idea-implement` step numbers exist in `PREFERENCES.md`, `fo-doc-audit/SKILL.md`, and `fo-session-retro/SKILL.md` — these break silently when steps shift. Always update all cross-references in the same commit.
- **A skill declared non-interactive must not delegate into a skill that grills by contract.** Before wiring a delegation (e.g. `fo-session-retro` → `fo-extract-dna`/`fo-harvest`), check the callee's constraints for mandatory `ask_user_question`/grilling steps — if the callee offers no non-interactive path, record a pending routing instead of invoking it. `fo-idea-create-adr`'s accepted-decision fast path is the model: a callee can expose an explicit skip contract for callers that carry an already-made decision with justification. Added with the session-retro auto-accept change (2026-10-28).
- **`forge <cmd>` prints nothing on validation failure — diagnostics come only via `--json`.** A bare `forge skill.validate` run exits 1 with empty stdout/stderr when violations exist; rerun with `--json` and read the `violations[]` array instead of assuming a clean pass or a crash. Applies to other forge validators as well. Discovered during the 2026-10-28 session-retro auto-accept edit.
- **A new `fo-*` skill that serves a pipeline phase must be wired into the implementation-document skills, not left manual-only.** Operators mostly invoke document-implementation skills (`fo-idea-implement`, `fo-idea-i-just-want-to-see-the-result`), not intermediate ones — a standalone skill that nothing calls is dead tooling. When adding a skill, wire the caller skills (`fo-idea-implement`, `fo-fix`, `fo-triage`, `fo-add-tests`, …) in the same change. Stated by the operator during the RFC-1440 grilling (2026-10-30).

The `concerns` field uses a four-level taxonomy (RFC-0523): `read-only` (no file modifications), `document-only` (modifies `.md` files only), `content-mutation` (modifies content `.md`/`.yaml` but not executable code), `code-mutation` (modifies `.ts`/`.astro` code). `skill.validate` enforces this via SKILL-12.

The optional `knowledge` field (RFC-0524) declares cumulative knowledge files as an array of file names relative to the SKILL.md directory (e.g. `knowledge: [qa-log.md, learned-principles.md]`). `skill.validate` enforces SKILL-13: declared knowledge files must exist. `create` syncs them to `.agents/skills/`. See `writing-great-skills` § Cumulative knowledge pattern for the entry format and mutation contract. RFC-0660 adds SKILL-19 (entry schema validity) and SKILL-20 (identifier uniqueness) for structured entries; RFC-0661 adds SKILL-21 budgets. RFC-1481 reserves upstream `K-NNNN` for Forge source entries and consumer-local `L-K-NNNN` for local entries. `forge doctor` warns on unresolved collisions; run `forge knowledge.conflicts.resolve --dry-run` to inspect the plan, then invoke it without `--dry-run` to resolve. The command serializes mutations; if it reports an existing lock, verify the owner before removing the stale `.forge/knowledge-conflicts.resolve.lock` directory.

### Validator return-type refactoring

When refactoring a validator's return type (e.g. from `Violation[]` to `{ errors, warnings }`), update **all** return points and call sites in the same commit. TypeScript catches missing fields in return objects, but does not catch semantic errors like warnings accidentally left in the violations array. After refactoring, search for all `return` statements and all call sites that destructure the result, and verify each one handles both `errors` and `warnings` correctly.

### Skill packs (RFC-0539)

Project-declared skill packs allow projects to manage their own skills under a project-specific prefix, separate from forge's portable `fo-` skills. Packs are declared in `forge.yaml` under `skillPacks`:

```yaml
skillPacks:
  - prefix: wg
    dir: packages/warpgogol-skills/skills
```

- `create` syncs pack skills alongside forge skills into `.agents/skills/`.
- `skill.validate` validates pack skills with SKILL-01..13 plus SKILL-14 (pack skill name must start with pack prefix), SKILL-15 (non-forge skill may not use `fo-` prefix), and SKILL-17 (no platform RFC/ADR ids or platform names).
- SKILL-07 enforces asymmetric dependency direction: pack skills may depend on forge skills, but forge skills may not depend on pack skills (breaks portability).
- `skill.list` includes pack skills with `pack:<prefix>` annotation.
- `doctor` checks for stale/missing pack skill copies and validates `skillPacks` config (unique prefixes, unique dirs, no `fo` prefix, dir exists).
- **RFC-0552:** `create` (via `runInit`) and `upgrade` (via `syncPackSkills`) detect pack skills whose name conflicts with a Forge skill name. Conflicting pack skills are skipped (not copied to `.agents/skills/`) and reported in `skippedSkills` on `InitResult` and `UpgradeResult`. The `forge-bootstrap` skill reports skipped skills to the operator during onboarding. The `forge-bootstrap` skill also runs `git init` for greenfield projects without a `.git` directory and commits synced skills to git.

## Import rules

- `src/` must NOT import from `@warpgogol/werkstatt-engine` or any kernel package.
- All `os/` directories are autonomous (RFC-0940 `runtime` field) and must NOT import from `@warpgogol/*` packages — FORGE-AUTONOMY-01 (enforced by `forge.autonomy.validate`) exempts only `os/werkstatt/`, the declared `"werkstatt-adapter"` bridging `@warpgogol/werkstatt-engine`.
- **Type-only `import type` from workspace packages still breaks the standalone build.** Standalone `tsc` resolves type imports — `@warpgogol/werkstatt-shared` contracts needed by forge must be inlined in `src/types.ts` (ADR-0019 autonomy). Do not suppress unresolved static imports with `@ts-ignore`: the suppressed type degrades to `any` and cascades into implicit-any errors downstream. The only sanctioned `@ts-ignore` imports are the dynamic `await import()` bridges in `os/werkstatt/handlers/workspace-deps.ts`. Discovered during the 5.3.0 export.
- Apps import forge modules from `@warpgogol/forge` (the package entrypoint re-exports all OS modules).
- **MUST** use `hasGeneratedMarker()` from `utils/index.ts` for detecting generated file markers — never use raw `content.includes("GENERATED")` which is fragile and breaks if the marker format changes.
- **Compass shared flags:** New flags for compass commands MUST be added to the shared `compassScanFlags` object in `os/compass/compass.module.ts`, not to individual command definitions. The `compassScanFlags` object is spread into all compass commands that use `flags: { ...compassScanFlags }`, ensuring the flag is available consistently across the command family. Per-command flags that are unique to one command may be defined inline.
- **CLI flags must be wired to behavior.** Every flag declared in a command registration MUST affect the command's output or behavior — not just be read and stored. A flag that is read but never used is dead code and a contract violation. When adding a flag, implement its behavioral effect in the same commit. Verify by searching for the flag variable name in the handler function body.
- **Profile-driven workspace detection is domain-neutral.** `workspaceTypes` from a stack profile must replace hardcoded workspace detection for ALL domains, not just software. Do NOT gate `checkNestedAgentsMd` or `discoverWorkspaces` by `isSoftwareDomain` — that silently skips the check for non-software domains (game, creative, etc.). When `workspaceTypes` is present, it fully replaces hardcoded detection; when absent, hardcoded detection is the fallback for all domains.
- **`command-registered` probes MUST fall back to command manifest.** The `command-registered` probe in `os/rfc/acceptance.ts` uses `commandRegistry?.listCommands()`, which only sees workspace-scoped commands (forge modules). App-scoped commands from `werkstatt-site/checks` are invisible to the workspace-level registry. Always include a `loadManifestCommandNames(workspaceRoot)` fallback, matching the pattern already used in `os/rfc/handlers/lifecycle.ts`. Without this, `rfc.acceptance.run` and `rfc.verification.emit` will falsely report app-scoped commands as "not registered".
- **`test` probes spawn vitest from the workspace root.** `spawnVitest` in `os/rfc/acceptance.ts` runs `pnpm exec vitest run <file>` with `cwd: workspaceRoot` — test files referenced by RFC acceptance probes MUST resolve package-local fixtures via `dirname(fileURLToPath(import.meta.url))`, never `join(process.cwd(), ...)`. A `process.cwd()`-relative fixture path passes under `pnpm --filter <pkg> vitest` yet fails under the probe. Discovered during RFC-1281 acceptance: the committed-fixture test was green in-package and red as a probe until the path resolution moved off `process.cwd()`.
- **Compatible `test` probes batch into ONE instrumented Vitest run (RFC-1489).** `runProbeSet` in `os/rfc/acceptance.ts` is the single shared execution point for declared probe lists — `rfc.acceptance.run`, `rfc.verification.emit`, `rfc.verification.refresh`, and the stamp re-emit all route through it. The planner (`os/rfc/probe-batch.ts`) groups a maximal contiguous run of `test` probes sharing one effective timeout bound (`timeoutMs ?? 120s`) into a single `pnpm exec vitest run <files> --reporter=json --outputFile=<tmp>` spawn; each probe is attributed only to its own `(file, testName)` slice of the JSON report, and a missing file/report yields `unverified`, never a pass. `run`, `page`, `proof`, and every non-`test` kind are barriers — they split segments and always run individually; a singleton `test` segment keeps the legacy per-probe spawn. `--no-batch` on all three commands forces the legacy path for debugging. `rfc.validate` reads non-target corpus files frontmatter-only via `readRfcFrontmatter` (bounded 64 KiB head read, full-parse fallback past the bound) — a rule needing a non-target `body` is a design smell to escalate, never to accommodate.
- **Generated-docs regen commands are inconsistent about persistence — most write directly, `rfc.index.generate` needs `--write`.** `command.manifest.generate`, `docs.commands.generate`, `validator.inventory.generate`, and `ecosystem.manifest.generate` all persist their output on a plain run; `rfc.index.generate` (and the decision-log regen) only reports unless `--write` is passed. Passing `--write` to a command that does not declare it is a KERNEL-FLAG-01 error — check the flag list before assuming a no-op regen actually wrote. Discovered during RFC-1281/1283 stamping: `rfc.index.generate` silently left the index on `accepted` until re-run with `--write`; during the REVIEW-CODE-2026-10-15-03 fix pass `--write` on `command.manifest.generate` failed as an unknown flag.

**`forge run <cmd>` is not a verb.** The standalone `forge` CLI dispatches bare registry names only (`forge compass.migrate`, `forge docs.archive`) — there is no `run` subcommand, and `forge run X` exits `Unknown command: run`. The canonical invoker for kernel/workspace commands is `werkstatt run <cmd>` (or `pnpm exec werkstatt run <cmd>`); `pnpm --filter @warpgogol/forge run <cmd>` runs package scripts, not commands. `command.docs.lint` catches this shape in docs; nothing catches it in agent shell invocations. ## RFC frontmatter: commands.changed (RFC-CMD-03)

The `commands.changed` field in RFC frontmatter must only list **registered CLI commands** (e.g. `compass.audit.baseline`, `mission.materialize`), not internal functions or handlers (e.g. `acquireLock`, `releaseLock`). `rfc.validate` enforces this via RFC-CMD-03: every entry in `commands.changed` must match a live command in the registry. Internal functions that are not registered as CLI commands must not appear in `commands.changed` — use `packagesImpacted` to indicate which packages were modified. The registry checked is the **werkstatt kernel registry**, not the standalone `forge` CLI — a command that works via `forge <cmd>` may still be unregistered in the kernel (e.g. `profile.validate` resolves to a different site-level command under `werkstatt run`). Verify registration via `werkstatt run <cmd>` or `docs/command-manifest.generated.yaml` before listing. Entries must carry the **qualified registered name**, not a CLI alias or unqualified short form — `doctor`, `upgrade`, `skill.validate` all fail because the registry holds `forge.doctor`, `forge.upgrade`, `forge.skill.validate`. RFC-CMD-03 only evaluates `commands.changed` at `status: implemented`, so a draft's green `rfc.validate` is no proof — qualify the names at authoring time or the failure surfaces immediately after `rfc.implement.stamp`. Discovered during RFC-1481 stamping.

## RFC frontmatter: YAML backtick quoting

YAML plain scalar values that **start with a backtick** (`` ` ``) must be double-quoted. Backtick is a reserved character in YAML plain scalars — the parser fails with "Plain value cannot start with reserved character `" and `rfc.implement.stamp`reports "Could not parse target RFC" (RFC-IMP-01). This commonly affects`successSignals`, `nonGoals`, and other list items in RFC frontmatter that reference code identifiers in backticks. Always quote such strings: `` - "`doctor`reports domain information" `` instead of `` -`doctor` reports domain information ``.

**Agent action:** After creating an RFC with `rfc.create`, scan the generated `successSignals` and `nonGoals` sections for unquoted backtick entries. Fix them immediately before committing. This prevents a recurring pattern where `ecosystem.manifest.generate` and `rfc.implement.stamp` fail on RFCs created with backtick-heavy frontmatter.

**Diagnostic:** If `rfc.implement.stamp` fails with `Could not parse target RFC` (RFC-IMP-01), the RFC frontmatter has a YAML syntax error — not a missing file. Check for unquoted backtick values first.

## RFC command lifecycle validation (RFC-CMD-02)

`getLiveCommands` in `os/rfc/handlers/lifecycle.ts` always merges `commandRegistry.listCommands()` with `docs/command-manifest.generated.yaml`. This is necessary because lazy-loaded modules (e.g. `leitstand`) are not loaded when `rfc.validate` runs, so their commands are absent from the registry but present in the manifest. Never change this to a fallback-only pattern (using manifest only when registry is empty) — that produces false-positive `RFC-CMD-02` violations for commands from lazy-loaded modules.

**After registering new commands in `tools/kernel.config.ts`, always run `command.manifest.generate` before `rfc.implement.stamp` AND before `rfc.verification.emit`.** Without this, `docs/command-manifest.generated.yaml` is stale and `rfc.validate` fails with RFC-CMD-02 ("implemented RFC lists X under commands.added, but no live command is registered"). The manifest is the source of truth for lazy-loaded command discovery. The `command-registered` acceptance probe in `rfc.verification.emit` resolves commands via `getLiveCommands` (registry + manifest merge) — a newly registered command missing from the manifest fails the probe with "not registered" even though `werkstatt run <cmd>` works. Discovered during RFC-1097 stamping.

**The same manifest regen is mandatory for commands added inside an existing module's `commands[]` array** (e.g. `os/core/core.module.ts`) — no `kernel.config.ts` change is needed for those, but the probe still resolves via the manifest. Also rebuild `packages/forge/dist` (`pnpm run build`) when the standalone `forge` CLI or a dist-loading consumer must see the new command — `bin/cli.js` prefers `dist/` when present, and a stale dist silently shadows `src/` (the `dist-freshness` doctor check, RFC-1151, warns on exactly this). Discovered during RFC-1151: `memory.compact` failed the `command-registered` probe until the manifest was regenerated.

## RFC creation: DNA-establishing RFCs go through kind:command (satisfies gate)

Post-cutoff `rfc.create --kind=architecture|contract` requires `--satisfies DNA-N` and `assertSatisfiesIdsExist` verifies every id against `## DNA-N` headings already registered in `docs/architecture-dna.md` — an RFC that ESTABLISHES a new DNA invariant cannot cite a not-yet-registered id and fails creation. The convention: create a DNA-establishing RFC as `--kind=command` (satisfies optional there), cite the existing DNA ids it builds on (if any), and register the new invariant in `docs/architecture-dna.md` through the normal DNA flow — the RFC body documents the establishment. Precedent: RFC-1337 created `page.render.check` as `kind: command` with `satisfies: [DNA-112]` while establishing a new invariant. Discovered when `rfc.create --kind=architecture` refused a DNA-establishing draft (2026-10-29, F-0004).

## RFC draft authoring: V-15 title match, V-13 required sections

The body H1 (`# RFC-XXXX: <title>`) must byte-match the frontmatter `title` field — markdown decoration (e.g. backticks around `werkstatt run`) in one but not the other trips V-15 ("title does not match body heading"). Author the H1 identical to the frontmatter scalar. `## Rollout` (and the other template sections) must exist as **top-level `## ` headings** — a `### Rollout` nested under `## Design` trips V-13 "Missing required section". Run `rfc.validate --id <id>` on every draft before committing; warnings are the last cheap gate. Discovered during the RFC-1309..1312 draft batch (2026-10-16).

**`rfc.create` near-duplicate gate (RFC-1467).** Terminal-kind precedents (`rejected-rfc`/`superseded-rfc`) scoring ≥12 against the title are blocking: `rfc.create` refuses and lists the colliding ids — re-run with `--revisit RFC-XXXX` naming one of them to acknowledge; the scaffold then cites it in `related:` and injects a `> NEEDS CLARIFICATION:` marker in `## Decision` requiring the draft to state why it differs from the rejection/supersession rationale. A `--revisit` id absent from the colliding set is refused with the valid candidates listed. The warning band (scores 8–11) is non-blocking: ids are cited in `related:` with the same NEEDS CLARIFICATION marker. `rfc.validate` mirrors the create-time gate via V-52: a draft whose title scores ≥12 against an uncited terminal precedent is a blocking violation — cite it via `related`/`amends`/`supersedes`/`supersededBy`. Discovered during F-0051 (2026-10-31): RFC-1462 re-proposed rejected RFC-1312 unlinked; caught by operator review.

## RFC batch authoring: rfc.create serialization and V-18 cascade triage

**Never invoke `rfc.create` concurrently.** ID allocation scans `docs/rfcs/` (and its archive) for the highest number, so two parallel creates race on the same next id — run creations sequentially within a batch. Discovered during the RFC-1412..1418 `site-surface-maturity` batch (2026-10-27).

**V-18 `related "RFC-XXXX" does not match any existing RFC` can originate in the *referenced* file, not the reporting one.** `rfc.validate` builds the id set by parsing every `docs/rfcs/` file; a single file whose frontmatter fails YAML parsing is absent from that set, so every sibling listing it under `related:` reports V-18 against itself. Triage order for a V-18 cluster: find the common referenced id and validate/repair *that* file's frontmatter first — one fix clears the cascade. Recurring trigger: an unquoted flow-sequence item containing a colon (e.g. `- Deferred: reason here` under `nonGoals:`) is read as a nested mapping and breaks the whole document — quote list items that contain `:` (same family as the backtick rule above). Discovered during the same batch: one colon-bearing `nonGoals` item in RFC-1417 produced V-18 errors in RFC-1414 and RFC-1416.

## RFC status transitions: rfc.implement.stamp is exclusive (V-16)

`rfc.implement.stamp` is the **exclusive atomic path** for accepted → implemented transitions. It atomically sets `status: implemented`, `implementedAt`, and `updatedAt` together. **NEVER** manually edit RFC frontmatter to set `implementedAt` or change `status` to `implemented` — this bypasses the atomic guarantee and risks leaving `status` and `implementedAt` out of sync. V-16 enforces this as an error: `status: accepted/draft` with `implementedAt` set, or `status: implemented` with empty `implementedAt`, both fail `rfc.validate`. After implementing an RFC, run `rfc.implement.stamp --id RFC-XXXX` to stamp it (auto-detects the implementation commit via `git log --grep` when `--implementation-commit` is omitted, RFC-0756; pass `--implementation-commit <sha>` to override). **`--implementation-commit` takes a git SHA, not the version printed by `ecosystem.commit`** — passing `6.316.121` fails RFC-IMP-03 ("not reachable from HEAD"). Resolve the SHA via `git log --oneline --grep="<message>"`. Discovered during RFC-1139 stamping.

**`--check-criteria` (RFC-1322) collapses the flip→emit→commit tail into the stamp — and since RFC-1483 it is the default path.** The stamp auto-checks every unchecked acceptance criterion whose `(evidence: ...)` annotation resolves (`test:<path>` / `file:<path>` / `<path>:<line>` must exist on disk; `probe:AC-N` must bind a passing probe in the evidence envelope), refreshes a missing/malformed/stale envelope in-process via the standard emit path (inside the RFC-IMP-05 lock, after the read-only gates pass), and lands the checkbox flips + frontmatter mutation in one atomic write — reporting every applied repair under `repaired[]`. Unresolvable or absent annotations abort with STAMP-CHECK-01 naming the criterion ids — the stamp certifies, so it resolves evidence rather than trusting annotations. `--check-criteria` remains an accepted alias; `--no-repair` restores the pre-repair blocking gate for audits. The default invocation is `rfc.implement.stamp --id RFC-XXXX --implementation-commit <sha>`; afterwards a **single commit** covers the stamped RFC file, the regenerated `docs/rfcs/verification/<id>.generated.yaml` envelope, and `docs/metrics/rfcs/<id>.metrics.yaml` — no intermediate checkbox or emit commits.

**Never hand-flip `[x]` checkboxes after `rfc.verification.emit`.** A manual checkoff mutates the RFC file after the envelope's `rfcFileHash` was computed → RFC-IMP-09 blocks the stamp and costs a re-emit + extra envelope commit. The atomic path is `--check-criteria` (flip + envelope refresh inside the stamp lock); if criteria were already checked by hand, re-run `rfc.verification.emit` and commit the envelope before stamping. Discovered during RFC-1459 stamping (F-0053).

## RFC-1306: rfc.evidence.sync + stamp --sync (kernel-host invoke port)

`rfc.evidence.sync [--id RFC-XXXX] [--dry-run]` re-runs the generated-artifact chain in dependency order (`checks.commands.generate` → `command.manifest.generate` → `validator.inventory.generate` → `docs.commands.generate` → `ecosystem.manifest.generate` → `rfc.verification.emit --id <rfc>` when `--id` is given) by delegating each step by name through `context.invoke` — the optional command-execution port the engine executor populates on `KernelRuntimeContext`/`ForgeRuntimeContext`. It stops on the first failing step (EVIDENCE-SYNC-02) with the child's diagnostics verbatim and never re-enters itself. `rfc.implement.stamp --sync` runs the same chain before the stale-evidence gate; plain stamp behavior is unchanged.

**Fail-closed contract:** under the standalone `forge` CLI there is no kernel host, so `context.invoke` is absent and `rfc.evidence.sync`/`stamp --sync` return EVIDENCE-SYNC-01 ("requires the werkstatt kernel host") instead of crashing. Forge must stay runtime-autonomous — never import the engine to obtain the port; the field is structurally typed in `src/types.ts` and populated only by the host.

## ADR status transitions: adr.implement.stamp commit reference (ADR-IMP-03)

`adr.implement.stamp --implementation-commit <sha>` requires the commit to reference the ADR id — satisfied when the commit message contains the id **or** its changed-file list contains the `adr-xxxx-*` slug (`commitReferencesAdr`, `os/adr/handlers/implement-stamp.ts`). The message check is case-sensitive on the uppercase id — a COMMIT-02 lowercase scope id (`docs(adr-xxxx):`) does NOT qualify; only the path check accepts lowercase. For **post-hoc ADRs** (decision already implemented before the ADR was written), the historic implementation commit does not mention the id — pass the `adr: accept` or `trace:` commit instead; both qualify. Discovered during ADR-0103 stamping; case-sensitivity confirmed during ADR-0119 stamping (two linkage attempts failed before the accept commit qualified).

**`docs.archive` can move a stamped ADR mid-pipeline.** Terminal ADRs relocate to `docs/adrs/archive/<status>/` whenever ANY session's retro runs `docs.archive` — including a parallel session's. Resolve the ADR path by globbing `docs/adrs{,/archive/*}/adr-xxxx-*` and re-glob before each edit; never cache the `docs/adrs/` path across steps. `queue.validate`/`adr.validate` resolve archived files themselves. Discovered during the ADR-0119 stamp run: a parallel retro archived the file between stamp and the Evolution edit.

## RFC acceptance criteria: evidence annotation (RFC-IMP-02)

`rfc.implement.stamp` enforces RFC-IMP-02: every checked acceptance criterion (`- [x]`) MUST have an inline `(evidence: ...)` annotation. Parenthetical references without the `evidence:` keyword (e.g. `(promote.ts, 13 tests)`) do NOT satisfy the rule — the stamp fails with "checked criteria lack inline (evidence: ...) annotation". Always format as: `- [x] <criterion text> (evidence: <file paths, commands, or test counts>)`. Commit the annotated criteria before running `rfc.implement.stamp`.

## RFC acceptance probes: criterion binding and coverage (RFC-0997)

RFC-0997 binds acceptance probes to criteria via the `criterion: "AC-N"` field and adds three validation rules for post-cutoff RFCs (createdAt >= `2026-09-01`):

- **V-35**: every probe SHALL declare `criterion` referencing an existing `AC-N` id. Missing, malformed, or dangling `criterion` is a blocking error.
- **V-36**: every top-level checklist line (`- [ ]` / `- [x]`) in `## Acceptance criteria` SHALL start with a unique `AC-N:` identifier. Duplicate or missing identifiers are blocking errors.
- **V-37**: checked criteria evidence SHALL resolve — `probe:AC-N` must reference a criterion with at least one bound probe; `test:<path>` and `<path>:<line>` must reference an existing file. **Evidence annotations MUST NOT contain em-dashes (—) or nested quotes** — the V-37 parser breaks on `test: path — "description"` and reports the file as non-existent. **The `<path>` token MUST be the file path only — no AC-N suffixes, no descriptions, no extra text after the path.** The parser treats everything after `test:` until end-of-parenthesis as the file path; `test: packages/forge/os/rfc/file.test.ts AC-1` is reported as non-existent because the parser looks for a file named `packages/forge/os/rfc/file.test.ts AC-1`. Use simple `(evidence: test:packages/forge/src/tests/file.test.ts)` without em-dashes, nested quotes, or AC-N suffixes. Discovered during RFC-0998 and RFC-0999.
- **RFC-IMP-08**: `rfc.implement.stamp` blocks stamping for post-cutoff RFCs of kind `architecture`, `contract`, or `command` that declare zero acceptance probes. Policy and deprecation kinds are exempt.
- **Coverage report**: `rfc.validate --json` and `rfc.acceptance.run` emit a non-blocking `coverage` block per post-cutoff RFC with `totalCriteria`, `probeBackedCriteria`, `coverageRatio`, `uncoveredCriteria`, `unboundProbes`.
- **`file-contains` probe `pattern` is RegExp, not literal.** The `file-contains` acceptance probe compiles its `pattern` field via `new RegExp(pattern, "m")`. Parentheses, brackets, dots, and other regex metacharacters MUST be escaped (e.g. `\\(RFC-1023\\)` not `(RFC-1023)`). Unescaped parentheses silently fail to match and produce false "pattern not found" results. Discovered during RFC-1023 verification.
- **YAML escape sequences in `file-contains` probe patterns.** When a `pattern` field contains regex escapes like `\\*`, double-quoted YAML strings produce a YAML parse error ("Invalid escape sequence \\*"). Use single-quoted YAML strings for patterns containing backslash escapes: `pattern: '1 \\* 1024'` instead of `pattern: "1 \\* 1024"`. Single-quoted YAML treats backslashes literally. Discovered during RFC-1091 stamping.
- **`file-contains` probe must match source code, not computed values.** When a probe checks for a numeric constant, the pattern must match the literal source expression (e.g. `1 \\* 1024 \\* 1024 \\* 1024`), not the computed result (e.g. `1073741824`). The probe runs `new RegExp(pattern).test(fileContent)` against source text — it cannot evaluate expressions. Discovered during RFC-1091 AC-9 probe.
- **`test` probes can flake — re-run `rfc.acceptance.run` before investigating.** The probe spawns `pnpm exec vitest run <file>` from the workspace root with `stdio: "ignore"`; a transient spawn/pnpm-resolution race can produce a spurious `exitCode=1` on an otherwise green file. Reproduce manually first (`pnpm exec vitest run <path>`); if green, simply re-run `rfc.acceptance.run` — it passed deterministically on retry during RFC-1196 stamping (twice).

## Evidence freshness gate + post-stamp re-emit (RFC-1271)

`rfc.implement.stamp` carries the stale-evidence chain — envelopes under `docs/rfcs/verification/` must describe the RFC's current bytes:

- **RFC-IMP-09 (blocking):** before mutating frontmatter, the stamp recomputes `rfcFileHash` (whole RFC file) and `acceptanceHash` (deep key-sorted probe serialization — nested `expect`/`schemaInline` fields are bound, no key filtering) and blocks on mismatch, missing hash fields, a committed envelope with a deleted `acceptance:` list, or a malformed/non-object envelope. Repair: `rfc.verification.emit --id <rfc-id>` then commit the envelope — except probe deletion, where emit skips probe-less RFCs: restore the probes first, or delete the stale envelope.
- **Post-stamp re-emit is automatic:** the stamp's own frontmatter mutation (`status`, `implementedAt`, `updatedAt`) would stale `rfcFileHash` by construction, so probe-bearing RFCs get their envelope re-emitted in-process right after the mutation writes — a successful stamp never leaves a stale envelope. Re-emit failure is non-fatal (warn + manual re-emit), matching the metrics-generator pattern. `--dry-run` never emits.
- **`emit --check` recomputes, never writes:** `rfc.verification.emit --check --id <rfc-id>` re-runs probes and compares the committed envelope on non-volatile fields (`rfcFileHash`, `acceptanceHash`, `probes.length`, `probes[].ok`, `overall`) — ignores `emittedAt`, `commit`, `durationMs`, `workingTreeDirty`, `kernelVersion`. Exit 1 + named `mismatches` on divergence. The PR workflow runs this on envelopes changed in the diff; hash freshness binds bytes, `--check` re-execution is what detects forged `ok`/`overall`.
- **Probe/RFC metadata fields:** probes MAY carry `expectationSource` (`self|requirement|independent|external`) and `limitations` (both shape-checked in `acceptance.ts`); RFC frontmatter MAY carry `verificationTier` (`standard|high|formal`, V-43 enum check — portfolio rigor stays policy-level, not a gate); skills MAY carry `notApplicableWhen`/`costNotes` (`src/skill-schema.ts`).
- **V-23 archive exemption:** `docs/rfcs/archive/**` skips the evidence-presence rule — archived RFCs are frozen history (precedent: V-13, RFC-DIR-01); the exemption is path-scoped and does not forgive failures in the active corpus.

## RFC criteria content rules: phase separation, reject checklist, criterion versioning (RFC-1006)

RFC-1006 adds five validation rules for post-cutoff RFCs and ADRs (createdAt >= `2026-09-03`):

- **V-38**: `accepted`/`implemented` RFCs with unchecked `DR-N` items in `## Document readiness` section are blocking errors. Document readiness criteria (`DR-N`) are separated from system conformance criteria (`AC-N`).
- **V-39**: acceptance criteria containing `SHALL ... and ...` joining two verb phrases are non-atomic — split into separate criteria.
- **V-40**: acceptance criteria containing unbounded quantity triggers (`fast`, `scalable`, `low latency`, etc.) are blocking errors — state a specific number.
- **V-41**: acceptance criteria containing weasel verbs (`handle gracefully`, `robust`, `works correctly`, etc.) are blocking errors — replace with a specific observable behavior.
- **V-42**: malformed criterion supersession annotations (`> Superseded AC-N (YYYY-MM-DD): <reason>`) are blocking errors. Superseded criteria are excluded from the unchecked count.

V-39..V-41 also apply to post-cutoff `implemented` ADRs via `adr.validate`. Pre-cutoff RFCs and ADRs are exempt. The reject checklist is conservative — it uses closed trigger lists, not semantic analysis. See `packages/forge/skills/fo/fo-idea-create-rfc/acceptance-criteria-standard.md` for the canonical authoring guide.

- **Section extractors in `validate-rules.ts` MUST call `stripFencedCodeBlocks(body)` before regex-matching markdown sections.** RFC documents contain fenced code blocks with example headings and checklists. Without stripping, extractors like `extractDocumentReadinessSection` and `extractAcceptanceCriteriaSection` match headings inside code blocks, producing false-positive validation errors (e.g. V-38 reporting unchecked criteria from a code block example). The `stripFencedCodeBlocks` helper removes all ` ```...``` ` blocks before extraction. Any new section extractor added to `validate-rules.ts` must follow this pattern.
- **Living-spec heading mechanics use `fencedLineIndexes`, not `stripFencedCodeBlocks`** (RFC-1232): `os/spec/live-spec-shared.ts` masks fence-interior lines for heading detection while keeping them byte-present for section mechanics — merge/rebuild must preserve fence content verbatim, so stripping (which removes blocks) is the wrong tool there. Every `#{3,}`/`## ` scan in that module consumes the fence map; new heading-sensitive helpers must too.

## Git-derived evidence origin (RFC-1330)

- `rfc.verification.emit` / `rfc.verification.refresh` attach `origin` (`declared`, `derivedOrigin`, `effective`, `reason`) to each probe record for RFCs created on or after `RFC_ORIGIN_CUTOFF` (`verification-origin.ts`). Range: base = oldest commit adding `status: accepted` to the RFC file, head = `HEAD`; all in-range commits count regardless of subject. `origin` is volatile envelope context — `emit --check` never compares it.
- Derivation: a probe declaration added/changed after acceptance ⇒ `self`; a `probe: test` file touched in range ⇒ `self`; a `run` probe invoking a command from the RFC's own `commands` block ⇒ `self`. Commits carrying `X-Expectation-Origin: independent-verifier` + `X-Verifier-Report: <path>` derive `verifier` (effective `independent`). Presence kinds (`file-exists`, `command-registered`, non-doc `file-contains`/`json-schema`) derive `presence`. No acceptance transition in history ⇒ `unresolved` (counts as self).
- **V-44 (rfc.validate, error, post-cutoff):** a WHEN/IF criterion whose bound probes are all presence probes. Bind a `test`, `run`, or `page` probe.
- **RFC-IMP-10 (stamp, blocking):** a probe declares `requirement`/`independent`/`external` but derives `self`. Fix the declaration to `self` or obtain non-self evidence; never rewrite history.
- **RFC-IMP-11 (stamp, blocking since RFC-1333):** a `verificationTier: high` RFC has a WHEN/IF criterion without a non-self effective probe.
- **RFC-IMP-12 (stamp, blocking, RFC-1333):** a post-cutoff `verificationTier: high` RFC needs a committed `docs/reviews/acceptance/<rfc-id-lower>/acceptance-*.md` report with `verdict: pass`, `isolation: subagent`, and a `candidateSha` followed only by verifier-trailer or docs-only commits. `--waive-independent-verification "<reason>"` is operator-only and waives just the isolation requirement. Build the verifier input with `rfc.verify.workspace --id <id> --candidate <sha>` (git-free export; implementer in-range tests and the RFC's plan/review/session/queue docs stripped).
- Agents MUST NOT add the verifier trailer by hand.
- **Verifier-evidence files for `expectationSource: independent` MUST be introduced at a path with no prior git history.** Derivation walks `git log --follow` over the bound file's in-range commits and requires every touching commit to carry the `X-Expectation-Origin` + `X-Verifier-Report` trailer pair — but `--follow` also traces **copy detection** (a verbatim or near-verbatim copy aliases back to a non-trailer source commit, `C092`) **and** same-path delete/re-add cycles (the path itself stays tainted; a content rewrite does not break the chain because the add commit still sees the copy-source in its parent tree). The only clean landing: delete the tainted path, then add the suite at a never-before-seen path under a trailer-carrying commit. Foreign mid-flight commits after the verifier's `candidateSha` likewise invalidate the IMP-12 binding — recover with a fresh `rfc.verify.workspace` export at HEAD plus a focused delta report, never by rewriting history. Discovered during RFC-1393 stamping (three recovery rounds).

## Reachable acceptance probe (RFC-1334)

- `probe: reachable` proves structural wiring. **Symbol mode** (`symbol` + `module`, optional `root`): the symbol must be value-imported by at least one tracked non-test module (`git ls-files`; type-only imports and bare re-exports do not count; barrels followed to depth 5; bare specifiers resolved through workspace `package.json` `exports`); with `root`, an importer must sit in the root's import graph. **Command mode** (`command`): the command's `reachableVia` in `docs/command-manifest.generated.yaml` must hold a `pipeline`, `invoker`, or `coverage` edge (a `delegated` coverage needs a `coverageNote`) **or** a live documentation mention (`werkstatt run <name>` / `forge run <name>`) in the supported doc surface — the probe unions structural edges with the mention scan (RFC-1351). Exactly one mode per probe.
- `reachableVia` carries structural edges only — documentation mentions never enter the manifest. The mention scan is shared: `src/reachability/command-mentions.ts` (exported as `@warpgogol/forge/reachability`) owns the file globs, exclusions, and `RUN_MENTION_RE`/`FORGE_VERB_RE` vocabulary; both `command.coverage.validate` (COVERAGE-01) and the acceptance `reachable` probe consume it — never re-declare the regexes locally.
- `reachable` is a presence probe (RFC-1330): it cannot be the sole evidence for a WHEN/IF criterion (V-44).
- **V-45 (rfc.validate, warning, post-cutoff):** a command in `commands.proposed`/`commands.added` without a command-mode `reachable` probe.
- Do not satisfy a failing `reachable` probe with a dummy importer — wire the deliverable where the RFC says it belongs.
- **Operator-only commands still need a `coverage` edge.** A command invoked only via CLI (no pipeline step, no `executeKernelCommand` invoker) gets `reachableVia: []` in the manifest and fails the `reachable` probe. Declare `coverage: "operator" as const` + a `coverageNote` naming the invocation surface on the registration — the edge is structural and counts. Discovered during RFC-1336: all four `authority.*` commands are operator-CLI-only by design and needed the declaration before `rfc.acceptance.run` passed.
- **`probe: test` paths and `test:` evidence annotations are load-bearing.** The probed/annotated file must exist at the declared path before `rfc.implement.stamp --check-criteria` runs — the stamp resolves evidence literally and `rfc.acceptance.run` executes the file. Either write the test at the probed path or fix the annotation to the real path first. Discovered during RFC-1336: two AC probes pointed at prescriptive paths, so the suites were moved to `editorial/tests/signoff-delegation.test.ts` and `src/tests/rfc-validate-delegation.test.ts` to match.

## Outcome probes (RFC-1453)

- **`page` probes execute.** Per RFC, page probes are grouped by `target` and run through the project's `bindings.commands.outcomeBuild` (build, `{target}` substituted, exit 0 = built) and `outcomeServe` (long-running; first stdout line parses as `{"url": "http://…", "pid": N}`, killed via the process tree afterwards). Forge fetches `url + path`, checks `expectStatus` (default 200), `selector`, and `textPattern` over the served static HTML (`linkedom`). Sessions are per-invocation — one build + one serve per target, shared across that target's probes, disposed in `finally` (`os/rfc/outcome-probe.ts`).
- **Tri-state verdicts.** `ProbeResult.verdict` and `VerificationEvidenceProbeRecord.verdict` carry `pass | fail | unverified`; `ok === (verdict === "pass")`. `unverified` is reported when the outcome cannot be observed — missing bindings, build/serve failure, serve handshake timeout, fetch failure — and never counts as success. `rfc.acceptance.run` reports unverified as error-severity RFC-ACC-04 (failing probes stay RFC-ACC-01); RFC-ACC-03 "skipped" and the unconditional `ok: true` are gone. Envelope readers normalize absent `verdict` as `ok ? "pass" : "fail"`.
- **V-47 (rfc.validate, error, non-archived files):** a `page` probe without `target`. Archived implemented RFCs keep pre-field page probes as frozen history.
- **RFC-IMP-14 (stamp, blocking):** the implementation diff (`resolveImplementationRange` base..HEAD; fallback `git show --name-only <implementationCommit>` when no accepted base resolves) touching a `forge.yaml` `outcomeSurfaces` glob requires a passing outcome probe in the evidence envelope — a `page` verdict of `pass`, or a `run` probe whose command equals the normalized `outcomeBuild` binding (`pnpm exec ` prefix stripped, `{target}` substituted, whitespace collapsed). No surfaces or no touched path → the gate does not evaluate.
- **V-48 (rfc.validate, warning):** `packagesImpacted` touching an outcome surface without a declared outcome probe. Entry `x` maps to `packages/x` (verbatim when it contains `/`); touched when a glob's static prefix overlaps that directory.
- **`--waive-outcome "<reason>"` is operator-only** (same policy as `--waive-independent-verification`): converts the IMP-14 block into a warning, records `outcomeWaiver: {reason, by}` in the verification envelope, and the stamp commit must carry an `X-Outcome-Waiver:` trailer. Agents MUST NOT pass it unless the operator directed it in the current request.
- **`outcomeSurfaces` are repo-root-relative picomatch globs.** `forge.doctor` warns when surfaces are declared without both bindings or when a glob matches no file.
- **Forge stays project-agnostic:** it never names consumer commands (`mission.validate`, `outcome.serve`, `werkstatt`, …) — projects bind them under `outcomeBuild`/`outcomeServe`. The werkstatt host implementation is `outcome.serve` in `packages/werkstatt-site` (serves the active mission workpiece's dist on an ephemeral port and prints the handshake line).

## Fixed inputs (RFC-1455)

Values an RFC fixes for the shipped result (verbatim copy, labels, names, decided option values) are declared in a `## Fixed inputs` table — `| ID | Value | Source | Checked by |`, fence-stripped parse, `\|` escapes — and bound to one `AC-N`. **V-50 (error):** a row whose `Checked by` is missing/malformed/nonexistent, whose criterion binds no `page`/`file-contains` probe, or whose value is not literally contained in the bound probe's `textPattern`/`pattern`/`selector`. **V-51 (warning):** Design/Rollout verbatim markers without the section. Both gate on `createdAt >= RFC_FIXED_INPUTS_CUTOFF` and skip archived files; the parser/evaluator lives in `os/rfc/handlers/fixed-inputs.ts`.

## Review deviations (RFC-1454)

When a code review finds the implementation intentionally differs from the RFC, `fo-review` records it in the report's `designDeviations` frontmatter (`id`, `rfc`, `summary`, `resolution: fix|amend`) and the RFC records each `amend` in `## Deviations` as `- <id> (review <reviewId>): <what changed>`. **RFC-IMP-15 (stamp block):** a committed review report under `bindings.paths.reviewsDir/code` carrying an `amend` absent from `## Deviations` — or a malformed record — blocks the stamp. **V-49 (error):** a `## Deviations` entry whose `(review <reviewId>)` resolves to no committed report, or a section list line breaking the entry grammar. Committed reports only (`git ls-tree`/`git show` at HEAD); fenced examples never parse as entries. Gate/parser live in `os/rfc/handlers/implement-stamp-deviations.ts`.

- **Persist `fo-review` reports with canonical frontmatter keys — `reviewId:`, `rfcId:`, `verdict`, plus `designDeviations[]` when a finding is an intentional deviation.** V-49 and RFC-IMP-15 index committed reports by `reviewId` only — ad-hoc keys (`id:`/`rfc:`) make the report invisible to the provenance scan and fail `rfc.validate` with dangling references. Copy the template from `fo-review/SKILL.md` verbatim instead of inventing a compact shape. Discovered during RFC-1475 stamping (F-0062).
- **Audit every evidence probe's `expectationSource` before `rfc.implement.stamp`.** `independent` requires evidence produced outside the RFC's own command surface — a probe that IS one of the RFC's new commands is `self`. A misdeclared probe fails RFC-IMP-10 at stamp time. Discovered during RFC-1474 stamping (F-0063).

## Re-entrant werkstatt locks (RFC-0616)

`acquireLock` and `releaseLock` in `os/werkstatt/handlers/lock.ts` are re-entrant by PID. When the same process re-acquires a lock it already holds, `acquireLock` increments the `depth` counter instead of throwing. `releaseLock` decrements `depth` and only deletes the lock file when `depth` reaches `1` or is `undefined`. The `depth` field is `.optional()` in `werkstattLockSchema` — old lock files without `depth` parse successfully and are treated as `depth=1` via `?? 1` fallbacks. Agents MUST NOT assume `acquireLock` always throws on an existing lock file — it only throws when a **different** live process holds the lock.

## forge.yaml (RFC-0391)

`forge.yaml` is the machine-readable project configuration file at the project root. It records project name, stack, package manager, and docs paths. `create` creates it; `doctor` checks for it; `forge.agents.generate` reads it to produce `AGENTS.md`.

- **MUST NOT** run `forge.agents.generate` against this monorepo's root `AGENTS.md` — it is hand-written and carries no generated marker; the edit guard enforces this, do not bypass it.
- **MUST NOT** re-add any `@warpgogol/*` import to `packages/forge` source — `doctor` autonomy guard will fail.
- **MUST NOT** hand-edit a generated `AGENTS.md` in bootstrapped projects — edit `forge.yaml` and regenerate.
- **MUST NOT** delete or "fix" an unresolvable `profile:` field to silence `doctor` (RFC-1118). The `profile-id-known` check fails when the declared id is absent from the installed `@warpgogol/forge` catalog — the remedy is `forge upgrade` (config ahead of pinned forge) or correcting the id, never removing the field. Re-serialization preserves the declared id verbatim; `forge init`/`create` never overwrite an existing `profile:` with a detection result.

## Stack profiles (RFC-0392)

Stack profiles are YAML documents under `profiles/` describing a supported stack (detection markers, workspace layout, install steps, baseline files). `scaffold` creates a working pnpm + Turborepo monorepo from a chosen profile in an empty directory. The migration-adapter registry (RFC-0546) detects the stack of an existing project during `forge-bootstrap` transplant mode.

- **MUST NOT** scaffold into a non-empty directory — no `--force` flag.
- **MUST NOT** add stack profiles for stacks forge cannot scaffold end-to-end.
- **MUST** reference all template files in `profiles/<profile>-templates/` from the profile YAML (`workspaceTypes[].agentsMdTemplate` or `firstWorkspace.files`) or document them in the `agentsMdTemplate` file. Unreferenced template files are orphan artifacts that operators cannot discover.
- Shipped profiles: `typescript`, `phaser-game`, `godot-game`, `knowledge`, `forge-shell` (minimal — default for `create`), `site-workshop` (per-client Werkstatt workshops, RFC-1125).
- **`site-workshop` token-onboarding contract (RFC-1125):** the profile scaffolds a Werkstatt workshop that installs private `@warpgogol/*` packages. `forge create` runs a non-interactive npm-token probe (`npm-token-check.ts`) **before** `pnpm install` — it fails fast with a fixHint when the token cannot fetch `@warpgogol/werkstatt-engine` (`.npmrc` `_authToken` or `NPM_TOKEN` env honored; never a `--npm-token` flag). `forge.doctor` re-runs the same probe post-install. The profile never scaffolds `systems-cache/` inside the workshop root — it is a sibling directory created on demand by `sternsystem.register`. `sternsystem.register` blocks until `werkstatt.identity.json` and a signing key exist (run `identity.bootstrap` first). `werkstatt.platform.update` bumps `@warpgogol/*` deps and reports `pinnedPlatform` drift.
- **MUST** include a `.github/workflows/ci.yml` template in every stack profile's `workspace.files` list. The CI template MUST include `concurrency` (cancel superseded PR runs), `permissions: contents: read` at workflow level, `timeout-minutes` per job, `env: TZ: UTC` per job, `actions/checkout@v5`, and `actions/setup-node@v5` with Node 24. New projects inherit reliable CI from the scaffold — operators should not need to hand-write CI from scratch.

### Domain fields (RFC-0638)

The `forge/stack-profile@1` schema includes six optional domain-neutral fields that allow a profile to declare its domain model. All fields are optional — existing profiles without them parse and function identically.

- **`domain`** — string identifying the project domain (e.g. `software`, `game`, `book`, `music`, `illustration`). Used for profile detection and doctor output.
- **`terminology`** — map of universal concept keys to domain-specific terms (e.g. `artifact: "game"`). Open vocabulary; universal keys have built-in defaults exported as `TERMINOLOGY_DEFAULTS`. Missing keys fall back to the default term.
- **`artifacts`** — array of artifact definitions (id, extensions, produce/validate commands, determinism properties). Used by `doctor` for domain-specific health checks in follow-up RFCs.
- **`workspaceTypes`** — array of workspace type definitions (id, detection markers, associated skills, AGENTS.md template). Used by `forge.agents.generate` for per-domain workspace detection in follow-up RFCs.
- **`invariants`** — array of domain-specific invariant definitions (id matching `^[A-Z]+-\d+$`, rule text, severity). Schema only — enforcement is deferred to follow-up RFCs.
- **`register`** — string selecting the default behavioral register (`business` or `creative`). Used by `create` as a one-time default for new projects; existing `PREFERENCES.md` is never overwritten.

Types and schemas are exported from `@warpgogol/forge`: `StackProfileDomainFields`, `ProfileArtifact`, `ProfileWorkspaceType`, `ProfileInvariant`, `stackProfileDomainFieldsSchema`, `UNIVERSAL_TERMINOLOGY_KEYS`, `TERMINOLOGY_DEFAULTS`.

### Domain-aware commands (RFC-0640)

The following commands are domain-aware — they read domain fields from the stack profile and `forge.yaml` to adapt their behavior:

- **`profile.validate`** — validates profile YAML files under `packages/forge/profiles/` against the `forge/stack-profile@1` schema (including RFC-0638 domain fields). Supports `--id <profile-id>` to validate a single profile. Returns exit 1 if any profile is invalid.
- **`create`** — reads `domain`, `terminology`, `register`, and artifact-derived semantic bindings from the selected profile and writes them into `forge.yaml` (domain, terminology, bindings.commands) and `PREFERENCES.md` (register). When the profile has no domain fields, behavior is unchanged (software-domain fallback).
- **`doctor`** — reports domain info (domain, source, register, terminology, invariant count) as a `domain-info` check. Enforces profile invariants via the invariant engine as a `domain-invariants` check (RFC-0675) — invariants with a `check` declaration are actively verified (`filename-pattern`, `file-contains`, `file-not-contains`, `attribute-pattern`); invariants without `check` remain advisory. The `attribute-pattern` check kind (RFC-0694) validates attribute values on elements matching a tag selector — requires `elements` (array) and `attribute` fields (schema-enforced via `.refine()`). Reports `fail` for error-severity violations, `warn` for warning-severity. The `--strict` flag elevates `warn` to `fail` for `domain-invariants` and `profile-validate` checks. `--json` includes `invariantViolations` array in the `domain-invariants` check. Runs `profile.validate` as an advisory `profile-validate` check (warn status on failure, not gating — shipped profiles are forge-internal). Nested AGENTS.md check runs for all domains — profile-driven workspace types replace hardcoded detection when present. Domain is resolved via a three-tier chain: `forge.yaml` `project.domain` → stack profile `domain` → default `software`.
- **`forge.agents.generate`** — loads `workspaceTypes[]` from the matching stack profile and passes them to `discoverWorkspaces` for profile-driven workspace type detection. When the profile has no `workspaceTypes`, falls back to hardcoded detection (astro.config → app, Dockerfile → service, else package).

### Per-domain AGENTS.md templates (RFC-0643)

`forge.agents.generate` uses profile terminology and register to produce domain-appropriate AGENTS.md files. When no profile is loaded (or the profile has no domain fields), output is identical to the pre-RFC-0643 implementation — no regression for existing software-domain projects.

- **Root AGENTS.md templates**: Static prose (header, project section, paths section, conventions) is extracted to template files at `src/onboarding/templates/root-agents-business.md` and `root-agents-creative.md`. `selectRootTemplate(register)` returns the appropriate template. Dynamic sections (skills table, capabilities, behavioral layer) remain inline and are inserted at the `{{dynamicSections}}` marker.
- **Nested AGENTS.md templates**: `selectNestedTemplate(workspaceType, profile, terminology, fallback)` reads `workspaceTypes[].agentsMdTemplate` from the profile. Template paths are relative to `packages/forge/profiles/`. Absolute paths and parent-directory traversal (`..`) are rejected with a silent fallback to the hardcoded template.
- **Terminology substitution**: `substituteTemplate(content, terminology)` replaces `{{terminology.key}}` placeholders with resolved values. Runs on the final assembled content (after dynamic sections are appended), so the behavioral layer's fixed policy text also receives terminology substitution. Unknown keys resolve to the key name itself — no error.
- **`{{terminology.key}}` placeholder syntax**: AGENTS.md templates use `{{terminology.key}}` (double-brace), not `ref(bindings.terminology.key)` (skill syntax). The two are documented separately.
- **`details` field in `--json` output**: `AgentsGenerateResult` includes an optional `details` array with per-file metadata: `{ path, domain?, register?, workspaceType? }`. The `generated` field remains `string[]` for backward compatibility.
- **`profile` field in `forge.yaml`**: `create` writes `profile: <id>` to `forge.yaml`. `loadForgeConfig` loads the corresponding `profiles/<id>.yaml` and attaches it as `config.profile` (a `StackProfile` object). The profile object is stripped before serialization — `forge.yaml` stores the profile id (string), not the full profile.
- **Template comments MUST NOT use literal `{{placeholder}}` syntax**: `replaceProjectPlaceholders()` runs on the entire template content, including HTML comments. A comment like `<!-- inserted at {{dynamicSections}} -->` will have the placeholder replaced with the full dynamic sections content, breaking the comment and inflating the output. Use plain text names (e.g. `dynamicSections marker`) in comments instead of `{{...}}` syntax.
- **All template content MUST be external files, not inline `lines.push()` string arrays.** Fixed prose and policy text in forge generators (e.g. `agents-generate.ts`, `nested-agents-templates.ts`) must live in `.md` template files under `src/onboarding/templates/` or `profiles/`, loaded via `fs.readFileSync` with placeholder substitution. Inline `lines.push("### Section heading")` patterns for fixed text are a contract violation — they embed template content in source code, making it harder to review and maintain. Dynamic, data-driven content (tables generated from registry data, conditional sections from config) remains inline.
- **Template files read at runtime via `fs.readFileSync` MUST be listed in `package.json` `files` array.** TypeScript compilation (`tsc`) does not copy `.md` template files to `dist/`. Without an explicit `files` entry, template files exist on disk in development but are missing from the published npm package — the generator silently falls back to empty content. The test `src/tests/package-files.test.ts` guards this: it verifies that `src/onboarding/templates/` is in the `files` array and that all expected template files exist and are readable.
- **Profile object stripping before YAML serialization**: `loadForgeConfig` attaches a full `StackProfile` object to `config.profile`. Before serializing the config back to YAML (e.g. in `create` post-processing), the profile object MUST be stripped back to its string id. Otherwise `forge.yaml` contains an object instead of a string and fails schema validation on re-read.
- **Profile invariant `rule` fields containing colons MUST be double-quoted.** YAML plain scalars with colons (e.g. `rule: mode attribute must be one of: sequence, fixed, contain, fit`) cause "Nested mappings are not allowed in compact mappings" parsing errors. Always quote rule fields that contain colons: `rule: "mode attribute must be one of: sequence, fixed, contain, fit"`. This also applies to any other YAML string field in profile YAML that may contain colons.

## Bindings contract (RFC-0393)

The `bindings` section in `forge.yaml` de-hardcodes project-specific values from fo-skills. Skills reference bindings by key (e.g. `ref(forge.yaml bindings.commands.validateRfc)`) instead of hardcoding commands, paths, or terminology.

- `forgeBindingsSchema` + `resolveBinding(config, key, placeholders?)` are exported from `@warpgogol/forge`.
- `doctor` validates bindings: checks path existence, reports resolved/absent/invalid, and emits `defaultable-binding-null` notices for forge-CLI-backed bindings that are null (RFC-0540).
- `create` writes forge-CLI-backed defaults for commands forge provides (`validateRfc`, `validateAdr`, `implementStamp`, `specValidate`) and null for stack-dependent commands (`typecheck`, `test`, `scopedBuild`). The package manager from `forge.yaml` determines the runner prefix (`pnpm exec`, `npx`, `yarn exec`, `bunx`).
- `skill.validate` enforces SKILL-11: canonical skill bodies must not contain hardcoded `pnpm exec werkstatt run` or `docs/architecture-dna.md` in instruction lines (code blocks and `run:` directives). Supports `<!-- skill-lint-disable SKILL-11 -->` escape hatch.
- `skill.validate` enforces SKILL-17: skill files must not contain specific platform RFC/ADR ids (`RFC-\d{4}`, `ADR-\d{4}`) or platform names ("Warpgogol", "Warpgogol", "WarpGogol"). Generic "RFC"/"ADR" terms, generic placeholder ids (`RFC-XXXX`), file paths (`adr-0000-template.md`), and binding key names (`validateRfc`) are allowed. The `@warpgogol/forge` npm package name is excluded from the platform name check. Supports `<!-- skill-lint-disable SKILL-17 -->` escape hatch.
- `skill.validate` enforces SKILL-18: canonical forge skill bodies must not reference software-specific binding keys (`bindings.commands.typecheck`, `bindings.commands.scopedBuild`, `bindings.commands.test`) in instruction lines (code blocks and `run:` directives). Skills must reference semantic keys (`bindings.commands.validate`, `bindings.commands.produce`, `bindings.commands.verify`) instead. Supports `<!-- skill-lint-disable SKILL-18 -->` escape hatch. Applies to forge skills only, not pack skills.
- `skill.validate` reports violations in layers: the validator `continue`s past a file after its first failing check, so fixing a SKILL-01 frontmatter error can unmask previously hidden SKILL-09/SKILL-11 violations in the same file. After any frontmatter repair, re-run `forge skill.validate` and expect newly surfaced violations — iterate until clean. Discovered 2026-10-09 fixing the `wg-*` pack.
- Skills declare binding requirements in frontmatter: `bindings: { requires: [...], optional: [...] }`.
- Degradation contract: required binding unresolvable → skill refuses to start; optional binding absent → step skipped with `Degraded:` line in report.
- **RFC-0609: Binding templates must use flag format.** CLI binding templates in `FORGE_CLI_BINDING_DEFAULTS` and `forge.yaml` must use `--id {id}` (flag format), not `{id}` (positional). For example: `forge rfc.validate --id {id} --json`, not `forge rfc.validate {id} --json`. This applies to `validateRfc`, `validateAdr`, and any future binding that passes an identifier to a command.

### Semantic command keys (RFC-0639)

The `forge/bindings@1` schema includes five optional semantic command keys that work across all domains. These coexist with the software-specific keys (`typecheck`, `test`, `scopedBuild`) — they do not replace them.

- **`commands.validate`** — domain-neutral validation command (replaces `typecheck` for non-software domains).
- **`commands.produce`** — domain-neutral artifact production command (replaces `scopedBuild`).
- **`commands.verify`** — domain-neutral verification command (replaces `test`).
- **`commands.preview`** — domain-neutral preview command (e.g. dev server, live preview).
- **`commands.lint`** — domain-neutral linting command.

All semantic keys are optional with `null` defaults. `applyCliBindingDefaults` initializes them with `null` (they are stack-dependent, not CLI-backed). `doctor` does **not** validate semantic keys — they are opt-in per-domain, so reporting them as `absent` for projects that intentionally leave them `null` would be noise. Skills reference them via `ref(bindings.commands.produce)` etc.

### Terminology resolution (RFC-0639)

The `terminology` field in `forge/bindings@1` is non-optional with a `{}` default (changed from `.optional()` in RFC-0639). `resolveTerminology(config, terminology, key)` resolves a terminology key using a three-tier chain:

1. **Tier 1 — bindings override**: `config.bindings.terminology[key]` (per-project).
2. **Tier 2 — caller-provided**: the `terminology` parameter (typically `profile.terminology` from RFC-0638).
3. **Tier 3 — universal default**: `TERMINOLOGY_DEFAULTS` from `@warpgogol/forge` (re-exported from `profile-schema.ts`).

If the key is not found in any tier, the key itself is returned. The `terminology` parameter is `Record<string, string> | undefined` — a separate parameter, not embedded in `StackProfile` — so the function works whether or not RFC-0638 profile terminology is available.

`resolveTerminology` is exported from `@warpgogol/forge` and `@warpgogol/forge/config`.

## Output contract (RFC-0542)

Every forge CLI command's output ends with a **Next steps** block in pretty mode and a `nextSteps` array in `--json` mode. Each entry is `{ action: string, kind: "required" | "optional" }`.

- `renderNextSteps`, `renderIdeRecommendation`, and `generateHelp` are pure functions in `src/cli-output.ts` — importable by `bin/cli.ts` and unit tests.
- `create` prints an IDE recommendation (Windsurf tested, alternatives without guarantee) after the Next steps block in pretty mode.
- All forge CLI natural-language output is English regardless of `PREFERENCES.md` — `aiLanguage` governs agent chat, not the forge binary.
- `printHelp` is generated from the registry via `generateHelp` — no hand-maintained command list. `--help <command>` prints per-command flags and description.
- `ForgeNextStep` type and `nextSteps?` field are on `ForgeCommandResult` directly (cross-cutting), not inside command-specific `data`.
- Lifecycle commands (`create`, `scaffold`, `doctor`, `port.scaffold`) MUST populate `nextSteps`. Pass-state validators MAY leave the array empty.
- Future commands (`create`, `upgrade`) MUST conform to the `nextSteps` contract from day one.
- Skill reports (agent chat output) use the operator's `aiLanguage` and contain zero CLI commands, guides, or format references in user-facing text. The system hides all complexity from the operator. CLI output remains English per RFC-0542; only the skill (agent chat) uses `aiLanguage`. The `forge-bootstrap` welcoming report is the canonical example of this contract.

## Silent upgrade trigger (RFC-0554)

The `forge-bootstrap` skill step 0 silently checks `forge.syncedVersion` against the installed `@warpgogol/forge` version. If they differ, it runs `forge upgrade --update-npm` invisibly — the operator is never informed about migration, version numbers, or upgrade mechanics. The npm update is skipped automatically in monorepo environments (where `packages/forge/` exists). The `upgrade` CLI command remains available for manual sync (with or without `--update-npm`). This is not a dual-path: it is a single upgrade mechanism (`runUpgrade`) with two entry points (CLI and `forge-bootstrap`).

## Core behavioral layer (RFC-0548)

`forge.agents.generate` now includes a **Core behavioral layer** section in generated `AGENTS.md` files. This section is wrapped in `<!-- forge:begin behavioral-layer -->` / `<!-- forge:end behavioral-layer -->` markers and contains:

- **Intent-to-skill routing table** — generated from `triggerPhrases` fields in fo-skill frontmatter. Each row maps natural-language trigger phrases to the corresponding skill.
- **Fixed policy text** for 20 core behavioral areas: auto-grilling, auto-session-save, auto-review, context awareness, creator-facing communication, adaptive learning, proactive guidance, live operator feedback, register parameter, pushback policy, external capabilities (MCP), safety net, invisible quality, first creation moment, creative health, sharing and feedback, cultural awareness, indirect teaching, ownership, and commit policy (RFC-0551).
- **Conditional extended behavioral layer** (RFC-0549) — included only when the register is `creative` (read from `PREFERENCES.md` `register` field). Contains ten sections: personal connection, creative memory, emotional rhythm (questions not declarations), gentle accountability, creative partnership, visual thinking, audience empathy, creative companion (companion mode, `saveCompanionSessions` flag, pull-only inspiration feed), creative confidence (outcome-based praise, never refuse creative direction), and always-next-step (RFC-0551, supersedes the "at most one per session" anticipatory suggestion limit). Content is loaded from `src/onboarding/templates/behavioral-layer-extended.md`.

`create` auto-runs `forge.agents.generate` after `forge.init`, so newly created projects get the behavioral layer from day one. If generation fails, a warning is logged but the create command continues.

The `triggerPhrases` field in skill frontmatter is validated by SKILL-16: optional array of 1-5 natural-language strings (each 5-100 characters), only allowed on fo-category skills. Pack skills may not declare triggerPhrases. The field is named `triggerPhrases`, not `triggers` — agent-IDE skill loaders (Devin CLI, Windsurf) reserve `triggers` for invocation modes (`user`/`model`), and a phrase list there silently drops the skill from discovery. SKILL-22 rejects a raw `triggers` key on both forge and pack skills.

## Nested AGENTS.md generation (RFC-0611)

`forge.agents.generate` also generates nested `AGENTS.md` files for workspace directories (directories containing `package.json`). Workspace type is auto-detected by content markers:

- **app** — directory with `astro.config.*`
- **service** — directory with `Dockerfile` or `service.config.yaml`
- **package** — directory with `package.json` only
- Precedence: app > service > package

Workspace-type detection rules are defined in RFC-0611. Agents MUST NOT add new detection rules without an amending RFC.

The edit guard skips hand-written nested `AGENTS.md` files (no generated marker) and reports them in the `skipped` array. Generated files (with marker) are regenerated if content differs. `upgrade` also runs nested generation after skill sync. `doctor` checks for missing, stale (in-memory comparison), and hand-written improvement opportunities.

`forge.agents.generate` supports `dryRun` mode (RFC-0601 pattern): it renders content in memory without writing to disk, returning `renderedFiles` in the result. This is used by `doctor` for staleness detection.

- **Doctor stale check MUST use the same rendering pipeline as `forge agents generate`.** The stale check in `checkNestedAgentsMd` (`src/onboarding/doctor.ts`) must call `readPackageInfo` → `buildNestedAgentsMd(ws, config, packageInfo)` → `selectNestedTemplate(wsType, profile, terminology, fallback)` — exactly matching `generateNestedAgentsMd` in `src/onboarding/nested-agents-generate.ts`. Any divergence (missing `packageInfo`, missing `selectNestedTemplate`, missing `resolveAllTerminology`) causes false-positive stale reports for all generated nested `AGENTS.md` files. When modifying either function, verify the other stays in sync.

## Editable generated files: `forge:custom` boundary (RFC-1153)

Editable generated files (root `AGENTS.md`, nested workspace `AGENTS.md`) are split by a preservation boundary. The generated head above the boundary is regenerated on every run; the custom tail below it is carried over verbatim.

- **Marker** — a `forge:custom` line in the file's comment style (`<!-- forge:custom -->` for `.md`). The marker line belongs to the generated head; only the **first** occurrence splits the file. It is emitted by the merge — operators may place it deliberately, but emitters MUST NOT write `forge:custom` inside generated content itself.
- **Hint line** — the generator emits `<!-- Add workspace-specific guidance below this line. Everything below is preserved on regeneration. -->` directly beneath the marker.
- **Footer fallback** — legacy files without the marker resolve the boundary at the canonical template footer (the last non-empty line of the render). The fallback fires at most once per file; the merged output gains the explicit marker.
- **Fail-closed** — when no boundary resolves and content diverges, the write is skipped (`unmapped-customization`), never overwritten. `doctor` reports the same diagnostic; the operator adds the marker to set the boundary.
- **Restrictive-marker files are never unmapped** — a file bearing only `GENERATED_MARKER` (no "Safe to edit") is fully generator-owned (RFC-0081): the merge path overwrites it with the editable boundary contract (fallback to a fresh merge) and `doctor` reports divergence as `stale`, never `unmapped-customization`. Fail-closed skip applies only to `EDITABLE_GENERATED_MARKER` files.
- **Merge rules** — `splitEditableGenerated` / `mergeEditableGenerated` live in `src/utils/editable-region.ts` (pure, no I/O); boundary matching normalizes `\r\n` → `\n` (DNA-58 rule). Existing-file reads MUST go through `WorkspaceIO` (`io.readFile`), not bare `fs`.
- **Upgrade visibility** — `forge upgrade --dry-run` reports `nestedAgentsPlanned` (merged output differs from disk) and `nestedAgentsSkipped`; the executing path reports `nestedAgentsGenerated`/`nestedAgentsPreserved`/`nestedAgentsSkipped`.

## Extended behavioral layer (RFC-0549)

The extended behavioral layer is conditionally included in generated `AGENTS.md` files when the operator's register is `creative`. It adds ten behavioral policies additive to the core layer:

1. **Personal connection** — operator name at key moments, project story, deep purpose as compass.
2. **Creative memory** — unimplemented ideas, aesthetic preferences, creative influences.
3. **Emotional rhythm** — session mood via questions (not declarations), return after break, progress celebration.
4. **Gentle accountability** — unfinished intentions, deep purpose checks.
5. **Creative partnership** — sounding board (2-3 alternatives), creative constraints, anticipatory suggestions.
6. **Visual thinking** — visual previews, visual diffs, milestone gallery, voice consistency, tone matching.
7. **Audience empathy** — audience perspective, first-visitor test, emotional memory, project narrative.
8. **Creative companion** — companion mode (`saveCompanionSessions` flag), creative blocks, inspiration feed (pull-only MVP, `inspirationFeed: on|off`).
9. **Creative confidence** — outcome-based praise (not effort-based), gentle purpose-drift pushback (never refuse creative direction).
10. **Always-next-step** (RFC-0551) — the agent MUST always propose a concrete next step after any pause point. Supersedes the "at most one anticipatory suggestion per session" limit from Creative partnership (section 5).

Three surrogate-relationship mitigations: questions instead of declarations, outcome-based praise, and 90-day entry expiry for emotional observations in `operator-profile.md`.

`fo-session-retro` routes extended-layer insights to `operator-profile.md` with Zugangsstufen tags: emotional rhythm → `[Vertraulich]` with 90-day expiry, aesthetic preferences → `[Öffentlich]`.

## RFC commands frontmatter (RFC-CMD-01..03)

When an RFC transitions to `implemented`, `rfc.validate` enforces command lifecycle rules against the `commands:` frontmatter:

- **RFC-CMD-01:** A live command listed under `commands.proposed` but not `commands.added` is a violation. For implemented RFCs, newly created commands MUST be in `commands.added`, not `commands.proposed`. `commands.proposed` is only valid for RFCs in `draft` or `accepted` status.
- **RFC-CMD-03:** Every entry under `commands.changed` MUST be a registered live command (present in `docs/command-manifest.generated.yaml`). Pipeline names (e.g. `build.prepare`, `SITES_BUILD_PREPARE_PIPELINE`) are NOT registered commands — they MUST NOT be listed under `commands.changed`. If an RFC modifies a pipeline array, that is not a command registration change.
- **Stamp pre-flight chores (run after the last fix lands, before `rfc.implement.stamp`):** (1) re-run every generator whose inputs changed since the last regen — a post-regen metadata-text edit (e.g. a command `description`) drifts `docs/command-manifest.generated.yaml` and fails DRIFT-01 inside the stamp's own pre-flight; (2) run `rfc.verification.emit --id <rfc>` — a missing or stale evidence envelope fails RFC-IMP-06, and fixes landed after the first emit leave the envelope stale; (3) move implemented commands `commands.proposed` → `commands.added` (RFC-CMD-01); (4) when the RFC declares `supersedes`, set `supersededBy` on the superseded RFC's frontmatter — V-12 enforces the bidirectional link and blocks `rfc.validate` without it. All four surfaced during the wave-1 stamps (1486/1488/1487).
- **Acceptance probes run vitest from the repository root** — the runner's default 5 s timeout applies, not the package config's. Any probe-referenced test that loops git operations (worktree add/remove, branch fixtures) needs an explicit per-test timeout (`}, 15_000)`) or the probe fails while the same file passes under the package suite. Hit on RFC-1486 and RFC-1488 probes.

## Spec vendoring (RFC-0394..0397)

External specification packages are vendored as immutable snapshots under `docs/specs/<spec-id>/` with an integrity manifest and `forge-spec.yaml` projection.

- `forgeSpecModule` (in `os/spec/`) registers `spec.validate`, `spec.status`, `spec.materialize`, `spec.live.merge`, `spec.live.list`, `spec.live.show`, `spec.live.validate`.
- `spec.validate` enforces SPEC-01..13: integrity, schema, cycles, references, waves, duplicates, materializedAs, amendments, consumers hygiene (SPEC-12) and consumer-identity warning (SPEC-13, non-blocking).
- `spec.materialize` scaffolds RFC files for locally-owned front nodes with `specRef` traceability and writes `materializedAs` back to `forge-spec.yaml`. RFC-1240: `consumers:`-bearing nodes not matching `project.consumer` (or the `--consumer` flag) are foreign-owned — excluded from the front and satisfying dependents; result carries `foreignOwned`.
- `spec.status` projects per-node states, blockers, progress, and the `foreignOwned` list.
- Spec amendments (`docs/specs/<id>/amendments/amd-NNN-*.md`) are the only correction channel — snapshot files are never modified.

### Living feature specs (RFC-0711)

Living feature specs are mutable markdown documents under `docs/specs/live/<domain>.md` that reflect the current specification of a feature or module. Unlike vendored spec snapshots (DNA-55), living specs evolve through delta merges from archived RFCs.

- `spec.live.merge --id <RFC-XXXX>` extracts headings from the RFC's `## Design` section and merges them into the corresponding living spec. All-or-nothing: aborts on any heading conflict without writing. Use `--dry-run` to preview.
- `spec.live.list` lists all living specs with domain, title, lastMergedRfc, and history count.
- `spec.live.show --domain <name>` reads and returns a single living spec.
- `spec.live.validate` validates all living specs with rules V-LS-01..09 (frontmatter, domain/filename match, archived RFC references, history integrity, duplicate domains, duplicate namespaced headings/history, archive coverage, and content drift — V-LS-09 byte-compares the committed spec against a deterministic replay of its `history[]` via the shared `projectLiveSpec` core, modulo `updatedAt`; unreadable history RFCs report as warning-severity diagnostics).
- `docs.archive` automatically calls `spec.live.merge` for implemented RFCs with `liveSpec` frontmatter field after archiving. Rejected RFCs with `liveSpec` are skipped.

## NPM publish workflow

`pnpm run publish:forge <patch|minor|major>` (RFC-1252) is the **only supported forge publish path** — it bumps `packages/forge/package.json` + `forge.yaml` `syncedVersion`, commits the bump into `HEAD`, exports committed `HEAD` content via `repo-extract --from-head --no-push`, verifies the extracted repo against the same scripts standalone CI runs, and pushes with an automatic ours-merge reconcile on non-fast-forward. Major requires `ALLOW_MAJOR_BUMP=1`. CI on the extracted repo publishes to npm with provenance.

Do NOT use `npm publish`/`pnpm publish`/`git commit` for forge releases — direct repo-extract runs bypass clean-source verification, and manual `git commit` on `packages/**` is blocked by `hooks/pre-commit`.

**Workspace deps must use dynamic imports.** `@warpgogol/*` packages that are not published to npm MUST be imported via dynamic `import()` (see `os/core/handlers/workspace-deps.ts`), never static `import`. Static imports would fail at runtime when forge is installed standalone from npm. The `workspace-deps.ts` helper caches the dynamic import and throws a clear error message if the packages are missing.

### `.npmrc` token precedence

When publishing `@warpgogol/forge`, npm resolves the auth token from `.npmrc` files in precedence order: `packages/forge/.npmrc` (project) > `werkstatt/.npmrc` (workspace root) > `~/.npmrc` (user). A stale token in `packages/forge/.npmrc` silently overrides valid tokens in the other files. npm returns `404 Not Found` (not `403 Forbidden`) on PUT when the token lacks publish permissions — this is a deliberate npm security behavior that masks auth failures as missing resources. When rotating npm tokens, update ALL `.npmrc` files that contain a token, starting with `packages/forge/.npmrc`. All three files are gitignored.

### repo-extract operational notes

- **Extract destination**: `repo-extract` writes the standalone repo to `<werkstatt-parent>/packages/<destName>` (e.g. `../packages/forge`) when `projectDir` starts with `packages/` and no `destBase`/`--dest` override is set. When a push fails, reconcile in that directory.
- **Diverged remote export**: if `git push` is rejected because the remote has an export commit the local repo lacks, the remote commit is an older export snapshot fully superseded by the local one. Resolve with `git merge -s ours origin/main` + push — records the remote commit in history while keeping the newer export tree. Do NOT rebase (hundreds of `.coverage/` conflicts) or force-push.
- **Post-ship version sync is automatic**: after a successful extract+push, repo-extract commits `chore: forge version sync X → Y (post-ship)` back to the monorepo (one commit per file: `package.json`, `forge.yaml`). Do not manually `ecosystem.commit` the version bump afterward — verify with `git log` instead.

## Git command patterns in forge handlers

- **`git log --oneline` output includes a hash prefix** — the format is `<hash> <message>`, not `<message>`. When matching commit message patterns in `--oneline` output, do NOT anchor the regex to `^implement:` or `^feat:` — the line starts with the hash. Use a non-anchored pattern like `implement:\s+RFC-\d{4}\b` instead. Discovered during RFC-0625 V-32 implementation where `^implement:` failed to match `--oneline` output.
- **`execGit` helper pattern** — multiple forge handlers (`implement-stamp.ts`, `verification-evidence.ts`, `validate-rules.ts`, `validate.ts`) each define their own `execGit`/`execGitLog` helper wrapping `execFile("git", ...)`. These are candidates for extraction into a shared `os/utils/git.ts` utility.

## CLI invocation and test fixtures

- **Running forge CLI commands on the workspace root** — `pnpm --filter @warpgogol/forge exec forge <command>` runs from the package directory (`packages/forge/`), where `forge.yaml` is not found. To run forge commands against the workspace root (e.g. `doctor`, `rfc.validate`, `upgrade`), use `node packages/forge/bin/cli.js <command>` from the workspace root instead.
- **Golden fixture for `agents-generate`** — when adding or modifying sections in `agents-generate.ts`, the golden fixture `src/tests/fixtures/agents-generate-business-before.txt` MUST be updated to match the new generated output. The test `agents-generate-domain.test.ts` compares generated content against this fixture with `expect(content).toBe(goldenFixture)` — a mismatch fails the test.
- **SKILL-17 brand pattern must be case-sensitive** — the brand regex in `skill-validate.ts` uses a `@`-lookbehind to allow `@warpgogol/<pkg>` npm-scope references in skill instruction lines. Making the regex case-insensitive (`/gi`) defeats the lookbehind and false-flags every `@warpgogol` import as a brand violation. Keep the regex case-sensitive (`/g` only) so the `@`-scope allowance works correctly.
- **`vi.resetModules()` before `vi.doMock()` for Node builtins** — when mocking Node built-in modules (e.g. `node:child_process`) in vitest, `vi.resetModules()` MUST be called BEFORE `vi.doMock()`. Without `resetModules()` first, the module cache retains the original module and the mock is not applied on re-import via dynamic `import()`. After the test, call `vi.doUnmock()` and `vi.resetModules()` to restore. Discovered during `upgrade.test.ts` `--update-npm` mock testing.
- **Mock `execSync` for scaffold tests** — `runScaffoldProject` calls `execSync` to run `pnpm add` install commands, which fail in test environments without network access. Mock `node:child_process` with `vi.mock("node:child_process", async (importActual) => { const actual = await importActual(); return { ...actual, execSync: vi.fn(() => Buffer.from("mocked")) }; })` and use dynamic `await import("../onboarding/scaffold-project.ts")` after the mock. Use `vi.importActual` to preserve `execFile` (used by `promisify(execFile)` in forge/os/compass).
- **`runDoctor` profile resolution in tests** — `runDoctor` calls `resolveForgeRoot(workspaceRoot)` which searches for `packages/forge/` relative to the workspace root. In temp-directory tests, the forge package is not found, so profile-dependent checks (prerequisites, invariants) are silently skipped. Either pass `forgeRoot` in the `ForgeRuntimeContext` (preferred), or create a minimal `packages/forge/profiles/<id>.yaml` inside the temp directory.
- **Never hardcode `packages/forge` to locate the forge package root** — that layout only exists in this monorepo; in npm consumers forge lives at `node_modules/@warpgogol/forge`. Any code that resolves forge-root-relative resources (skills, profiles, fixtures) MUST take `context.forgeRoot` when provided (kernel/CLI set it) and fall back to `resolveForgeRoot(workspaceRoot)` guarded so an unresolvable root degrades the feature silently (empty list/skip) rather than throwing — bare temp-dir test workspaces rely on this. Regression-test consumer layout by symlinking the real package into `<tmpdir>/node_modules/@warpgogol/forge` and passing `forgeRoot: undefined`. Discovered during the `agents-generate` routing-table fix: `extractTriggerPhrases` used `path.join(workspaceRoot, "packages", "forge")`, so every npm consumer generated an empty intent-to-skill table (2026-10-01).

## RFC frontmatter: versionBump for prose-only policy RFCs

Prose-only policy RFCs (skill-text-only, no code/command/contract changes) MUST set `versionBump: none`, not `patch`. The `patch` value over-reports the SemVer impact — there is no runtime or API surface change. This was a recurring audit finding across RFC-0669, RFC-0670, RFC-0671, RFC-0672, and RFC-0673 (5 consecutive RFCs). Set `versionBump: none` at creation time for `kind: policy` RFCs that only modify `.md` skill files.

## RFC frontmatter: file system responsibilities table

Skill-text-only RFCs MUST include `packages/forge/AGENTS.md` in the file system responsibilities table with the note "No change needed — documents skill infrastructure, not individual skill behavior." This preempts a recurring audit finding (5 consecutive RFCs). The `packages/forge/AGENTS.md` file documents skill infrastructure (sync paths, validator rules, import constraints), not individual skill behavior — so it never needs updating when a skill's text changes.

## rfc.create title reuse

`rfc.create` may reuse the title from a previous invocation in the same session. After creating an RFC, always verify the generated filename matches the intended title before populating content. If the filename is wrong, delete the file and re-run `rfc.create` with the correct `--title`. Do not rename the file — the RFC ID is assigned by the command and must not be manually changed.

## rfc.archive scope and bulk frontmatter edits

- **`rfc.archive` moves files only from `docs/rfcs/` root into `archive/`** — it does NOT re-sort between archive subdirectories. An RFC whose status changes to `superseded` while already inside `archive/implemented/` stays there; the validator does not enforce the subdirectory. Discovered during the 2026-09-22 validation cleanup (16 RFCs transitioned to superseded in place).
- **Bulk frontmatter edits must handle both empty-field forms.** YAML serializes unset fields as both `closedAt:` (empty) and `closedAt: null` — a regex matching only `^closedAt:\s*$` misses the `null` variant. Match `^closedAt:\s*(null)?\s*$` when filling fields mechanically. Similarly, acceptance probe commands appear both quoted (`command: "site-kernel run ..."`) and unquoted (`command: site-kernel run ...`) — rewrite patterns must cover both.

## Profile-driven RFC conventions

All profile-driven RFCs (RFC-0674 onwards) MUST follow these conventions:

- **CLI flags**: every proposed command MUST support `--dry-run`, `--json`, and `--profile` flags. These are the standard Forge lifecycle flags.
- **Schema extensions**: all new profile schema fields MUST be optional (`z.optional()`) — existing profiles must continue to validate without changes.
- **No domain-specific logic in Forge core**: all behavior is driven by profile YAML declarations. Forge source must not import domain-specific packages or hardcode domain-specific rules.
- **File system responsibilities table**: every profile-driven RFC MUST list `packages/forge/src/profiles/profile-schema.ts` and `packages/forge/os/core/core.module.ts` in the table.

## Workflow file placement

Workflow files MUST live only in `.agents/workflows/`. Do NOT duplicate workflow files in `.windsurf/workflows/` — `.windsurf/workflows/` is IDE-specific config that does not ship to new projects via `create`. `.agents/workflows/` is the single source of truth for workflow definitions.

## Workflow files vs skill content

IDE-specific workflow files (`.windsurf/workflows/`, `.devin/workflows/`) MUST NOT duplicate skill content. Skills (`packages/forge/skills/`) are the portable unit — they ship to every new project via `create`. Workflow files are IDE-specific triggers that reference skills by name; they should not contain the protocol itself. If a workflow file grows beyond a trigger phrase + skill reference, move the content into the skill's `SKILL.md`.

## Kernel command handler pattern: pure function + thin handler

When a kernel command's logic needs to be called from two contexts — (1) a pipeline step via `KernelRuntimeContext` and (2) directly from another package without kernel types — split into a pure function + thin kernel handler.

- **Pure function**: `ensureThing(workspaceRoot: string, logger: { info: (msg: string) => void }): Promise<Result>` — no kernel types, callable from any package.
- **Thin kernel handler**: `runThing(input: KernelCommandInput, context: KernelRuntimeContext): Promise<KernelCommandResult<Result>>` — calls the pure function, wraps result in `KernelCommandResult`, catches errors → `exitCode: 1`.

This avoids the fragile alternative of calling a kernel handler with synthetic `input`/`context` from non-kernel code. The pure function is the reusable unit; the handler is the pipeline/CLI adapter.

**Custom result types:** When a kernel command returns a custom data type (not `CheckResult`), you cannot use `failResult`/`passResult` from result helpers — they return `KernelCommandResult<CheckResult>`, not your type. Build the `KernelCommandResult` manually: `{ data: result, exitCode: 0, summary: "ok" }` for success, `{ data: { ...nulls }, exitCode: 1, summary: msg }` for error.
